# GVE16 飞书交付

## 核心原则

以已核验的飞书 Wiki `ZsTVw7lTEi9rErknL9bcRfFunei` revision 40 为交互交付标准；以成功文档 `TVnddRv6FoGFE0xTSMkcKNSunpc` 为正文格式基准；以成功文档 `ZNWkd0Ke3oZCtAxDQA5ckxonnJS` 为原生 UE 画板的技术实现基准。三者职责不可互相替代。

先完整读取并遵循 `lark-shared`、`lark-doc`、`lark-whiteboard`、`gve16-planning-schema`、`gve16-feishu-whiteboard`。涉及发布或修复时，读取 [references/delivery-contract.md](references/delivery-contract.md)；涉及审核网站、视图切换或用户修改时，读取 [references/flowdoc-review-contract.md](references/flowdoc-review-contract.md)。

## 标准优先级

| 标准 | 约束范围 |
|---|---|
| 已核验 Wiki `ZsTV...` revision 40 | 交互阶段仅有两块原生 UE 画板，顺序为 `planning → competitor` |
| `TVnd...` | 标题层级、章节顺序、表格/说明对应关系、正文呈现 |
| `ZNWk...` | 真实 Section、截图与编号规则、父子页面及往返连线 |
| FlowDoc | 用户如何在全流程、环节和组件视图中审核与修改 AI 草稿 |

交互阶段的 UE 流转图只包含两个原生画板，顺序为 `planning → competitor`：`策划草图` 使用确认后的代表截图、组件编号、规则说明、straight 跳转/返回线和黄色待确认注记；`竞品参考` 仅使用用户上传的竞品截图和文件名，素材为空时显示黄色“待补充”。交互阶段不生成 UX设计，也不输出叙事、引导、红点提示章节。未来玩法策划使用单独的、证据特定的合同，不得从这份仅限交互的规则中推断。

## 强制执行顺序

严格按以下次序执行并保存文档 token、画板 token、请求 ID 和媒体映射：

1. 创建正文：按 `TVnd...` 的标题与内容槽位生成完整 XML，并嵌入恰好两个有序的原生 whiteboard 块，顺序为 `planning → competitor`。
2. 读取画板 token：重新 fetch 已创建文档，从 `<whiteboard token="...">` 获取真实 token。
3. 写入结构：先写 Section、标题、规则、标记、说明和连接器。
4. 上传代表帧：只选每个已确认环节/状态的代表帧，禁止上传全部证据帧。
5. 写入图片节点：使用白板作用域媒体 token 创建非零尺寸 `image` 节点。
6. 预览验收：导出图片，人工核对截图可见、顺序、标记、连线和文字。
7. raw 验收：检查节点类型、token、尺寸、数量、重复坐标和残留节点。

结构写入完成后不得再次 overwrite；否则媒体节点可能被抹除或失效。失败重试必须复用原文档和检查点，不得新建另一份文档。

## 交付边界

- “标题使用飞书原生编号”不得实现为在正文前复制一份“玩法目录”。目录只属于导航层；正文必须直接进入概述、画板与玩法章节。任何自动生成的标题索引都不得作为普通正文发布。

- 章节编号使用飞书原生有序列表块，不把 `1.`、`1.1` 等编号硬编码进标题文字。远端回读必须能识别 ordered block，并拒绝编号与标题重复。

- 正文不建立重复的“证据帧图库”，但当局部截图能直接说明当前规则、页面状态或空间关系时，应把经过确认的原图或局部裁切就近放在对应正文之后，并写业务含义说明。画板中的全局缩略图不能替代正文中可读的局部图示。
- 视频未明确展示的内容写“待确认”，不得用推断填满策划案。
- 只有预览验收和 raw 验收同时通过，才可报告成功并返回文档链接。
- 任何凭证、API Key、用户 token 均不得写入 Skill、日志或交付文档。
- FlowDoc 决定如何审核，GVE16 决定最终写什么；审核视图的数据结构不得变成飞书正文的新章节。

## 常见失败

| 现象 | 处理 |
|---|---|
| 飞书画板图片空白 | 重新以 whiteboard parent 上传媒体，禁止 data URI 或文档域 token |
| 画板可见但 raw 有零尺寸/重复节点 | 清理后重建干净结构，再上传代表帧 |
| 正文结构正确但标题漂移 | 逐项对照 `TVnd...`，不要套用 `ZNWk...` 的简版正文 |
| 上传 45/137 等大量帧 | 停止；按确认环节去重为代表帧 |

## 交付事故硬门禁（2026-08-12）

以下规则来自真实交付事故，任何一条未满足都不得宣称飞书交付完成：

1. P7 预览是正式文档的唯一排版基准。发布层必须消费与 P7 相同的有序交付清单，不得另起固定模板重新拼章节。
2. 章节、正文、就近截图、就近流程图、机制表格的相对顺序必须一致；禁止把流程图集中到独立图片区，或把正文中的图文关系拆散。
3. “策划草图”和“竞品参考”的网站预览与飞书画板必须使用同一份 SVG 载荷；节点、连线、文字、图片、坐标和顺序任一不同都判失败。
4. 已审核策划草图的 SVG、ID、所属章节和插入锚点视为不可变交付数据。迁移、重建和重新生成不得用自动图覆盖它们。
5. 策划草图中有截图证据的具名武器、强化效果、载具、怪物和关卡属性必须同步进入对应对象正文的 `attributeSections`；纯布局与泛化 UI 识别只留在画板。P7 与飞书渲染前重新执行同步，遗漏时阻断发布。
6. 发布前固定验收：核心对象全量扫描；画板事实与正文成对核对；泛化 UI 文本负向检查；`missingCount=0`；P7 与待发布飞书载荷逐条一致。没有具名证据时禁止为凑覆盖率扩写。
7. 图解不得截断同一编号规则组。完整业务步骤连续呈现后再放图；`afterFlowIndex`、`followUp` 和“后续章节展开/本节继续说明”等内部导航旁白不得进入正式正文。
8. P7 在嵌入式工作台中必须按容器宽度响应；空间不足时状态与飞书导出区整块换行，禁止逐字换行、按钮越界或隐藏导出入口。
9. P7 同源预览必须以真实表格展示飞书原生 `table` 载荷；只允许增加本地样式和横向容器，不得改变发布 XML。发布前逐表验证表头列数与每行单元格数一致。
10. 8 条以上且跨多个业务主题的长列表应组织为 2～4 个内容特定小标题；标题不得跨机制复用，不得使用“其他规则/规则与边界”等模板兜底，近义重复只保留一次。
5. 属性列表、数值清单、结算统计不能伪装成流程图。流程图必须存在动作节点、条件判断、分支/回流以及明确结果。
6. 飞书接口返回 `failed` 或 `partial_success` 一律判失败，不得展示为已发布。
7. 发布后必须重新读取远端完整文档，逐项比较标题顺序、正文块、表格、图片/画板锚点及首尾内容；不能只检查接口成功或文档存在。
8. 必须读取所有远端画板原始节点，检查节点数、图片数、空画板、重复图片和错误图解；仅有画板 token 不代表交付成功。
9. 内容指纹必须覆盖正文 XML、画板 SVG、素材及图解哈希。幂等键必须使用固定长度哈希，且变更发布载荷时同步升级版本。
10. 用户拒绝任一图解或排版后，立即停止外部写入。受污染文档只能在本地预览重新验收后整体重建，不得边修边覆盖正式文档。
11. 固定验收链：先把验收用例发给用户确认；再本地自检；再提供完整且不重复的证据截图；用户确认后才允许发布；发布后再做远端同版核验。

### 预览即交付验证

发布前生成有序交付清单，每项至少包含 `type`、稳定 ID、标题、所属章节和插入锚点。P7 正文直接预览飞书将发布的同一份内容；两个主画板直接预览飞书将写入的同一份 SVG。验收比较实际载荷哈希和顺序，不仅比较文字是否出现。

### 正文截图不可降级为文字

- `inlineFigures` 表示正文中的真实图片块，不是“对应截图：……”说明文字。
- P7 与飞书必须使用同一帧、同一裁切、同一图注和同一章节锚点；画板中的缩略图不能替代正文截图。
- 本地预览从任务素材路径加载真实图片；飞书先在同一位置创建 `img` 块，再以 `docx_image` 上传该本地文件。
- 图片缺失、图片块数量不一致、上传未返回 token 或远端回读无图片块时，必须阻断导出。禁止静默删除图片、移动到图库或改写成文字占位。
- 自检必须同时证明：图片像素实际加载、图注相符、前后正文位置正确、预览与远端图片块数量一致。
