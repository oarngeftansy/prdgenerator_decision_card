## 2. 正文合同

正文至少包含：定位说明、需求概览、UE 流转图说明与真实 whiteboard、完整交互流程、分环节规则、待确认项、状态与异常、验收项。

当 UE 流转图已经包含截图时，正文不再生成无上下文的“证据帧/参考画面”图库。但若单张截图或局部裁切能直接说明正文中的状态、操作、反馈、属性或空间关系，应在对应规则附近就近插图并写业务说明；画板总览里的缩略图不能替代可读的正文配图。

交互阶段不输出叙事、引导、红点提示章节。未来玩法策划必须使用单独的、证据特定的合同；不得从这份仅限交互的规则中推断未来玩法的规则域或内容。

## 3. UE 流转图合同

交互阶段只交付以下两个原生画板，严格按 `planning → competitor` 排列：

1. `策划草图`：使用确认后的代表截图、组件编号、规则说明、straight 跳转/返回线和黄色待确认注记。Section、编号和注记必须直接对应已确认的交互证据；未展示的规则保留“待确认”，不得猜测。
2. `竞品参考`：仅使用用户上传的竞品截图和文件名。素材为空时只显示黄色“待补充”，不得以交互视频、推断截图或规则文本补齐。

- 每个页面/弹窗使用真实 Section；不得只画一个像 Section 的矩形。
- 每个已确认环节只放能解释状态或跳转的代表帧；禁止上传全部证据帧。
- 截图上的红色编号与旁侧规则一一对应；黄色说明承载跨状态约束、重点或待确认项。
- 父页面到子页面使用带标签的实线直箭头；关闭/返回使用带标签的虚线直箭头。
- 图片必须是 `type=image`、`width > 0`、`height > 0`，且 `image.token` 为白板作用域媒体 token。

`ZNWk...` 的已验证实现含 2 个真实 Section、8 个有效图片节点和 2 条 straight connector；这是结构范式，不是所有项目的固定数量。

## 4. 发布协议

以下语义顺序不可调整：创建正文 → 读取画板 token → 写入结构 → 上传代表帧 → 写入图片节点 → 预览验收 → raw 验收。

上传每张代表帧：

```powershell
lark-cli.cmd docs +media-upload --parent-type whiteboard --parent-node <board_token> --doc-id <doc_token> --file <relative_image_path> --as user
```

将返回的 `file_token` 写入 raw 节点：

```json
{"type":"image","x":100,"y":100,"width":290,"height":510,"image":{"token":"<file_token>"}}
```

结构写入完成后不得再次 overwrite。图片阶段使用增量更新和稳定 idempotent token。

## 5. 双重验收

预览验收：截图真实可见；顺序与流程一致；编号不遮挡关键 UI；文字可读；实线进入、虚线返回；黄色说明位置正确。

raw 验收：

- 图片数等于去重后的代表帧数；
- 每张图片尺寸非零、token 非空且属于当前画板；
- 不存在零尺寸、重复坐标、重复 token 或历史 data URI 节点；
- Section、connector、编号和说明节点数量符合本次策划结构；
- 正文没有重复截图块。

任一验收失败都不得声明完成。

## 6. 失败恢复

保存 `doc_token`、`board_token`、创建 revision、请求 ID、已完成媒体映射。超时或授权恢复后从检查点继续；不得新建另一份文档。若 raw 已被历史失败节点污染，先重建干净画板结构，再按同一代表帧映射上传。
