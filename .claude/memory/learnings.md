# Learnings：历史踩坑（只追加）

## 2026-08-26：业务校验失败不能伪装成服务故障

- 失败表现：交互审核保存返回 400，因为当前 Stage 没有已观察的玩家操作；前端却统一显示“请检查服务状态”，使用户反复重启服务而无法解决业务缺口。
- 永久规则：409 revision 冲突先同步 canonical model；可识别的 400 原因映射为具体策划动作；其他 400 显示当前确认条件未满足；只有网络异常和 5xx 才提示服务故障。验收必须断言真实业务 endpoint、job、revision、错误原因与刷新后的 canonical 状态。

## 2026-08-26：发布回读必须同时覆盖后端与前端

- 失败表现：Brand Update 已运行、服务也重新启动，但 health capability 和 served JS 仍是一新一旧或全部旧版，已修复的问题在正式地址继续出现。
- 永久规则：每次发布同时回读 application manifest、后端 capability、HTML/JS/CSS marker 和至少一个关键前端文案；任一不匹配都判定部署未完成。服务 running、任务 revision 增长或普通接口 200 不构成版本证据。

## 2026-08-26：等价 Git 历史推送前必须验证对象哈希

- 失败表现：PowerShell 将未正确引用的 `HEAD^{tree}` 解析为空值，后续 ref push 有删除远端分支的风险；本次远端分支虽已立即恢复并安全推进，但流程本身不可接受。
- 永久规则：`commit-tree` 前把 tree、parent 和新 commit 分别校验为非空 40 位十六进制；再用 `cat-file` 核对 tree/parent，最后才允许精确 push。任何变量为空立即停止，绝不把空 refspec 交给 push。

## 2026-08-26：无法确认浏览器目标时不能宣称自动验收

- RDP 捕获可能因系统接口不支持失败，浏览器自动化也可能因无法确认当前 URL 被安全门禁停止。此时不得盲点、不得依据用户口述补造截图，也不得写“已跑完整流程”。
- 永久规则：保留阻断证据，先完成版本回读；恢复可控浏览器后，再在正式 URL 对真实项目执行按钮、URL、网络、控制台、刷新、编辑保存、失败重试和最终导出验收。

## 2026-08-25：高测试数不能替代跨层闭环与正式版本证据

- 失败表现：单页或本地回归通过后，相同问题仍在旧项目、新项目、迁移数据、P7 导出或正式 8010 复现；服务 running 也可能同时加载新后端和旧静态资源。
- 根因：同一业务事实存在 legacy/new/migrated/preview 多种表示，门禁分散在 P4–P7，修复只落一层；发布又没有把每个静态资源 marker 与应用 manifest 作为原子版本核对。
- 永久规则：每类缺陷必须审计生成、持久化、迁移、GET、前端投影、编辑、导出和重试的完整路径；发布时逐项回读 HTML/JS/CSS marker、health、manifest 和正式浏览器行为。自动测试数只证明已覆盖合同，不得推导架构整洁或正式上线。

## 2026-08-25：按钮文案必须对应真实状态变更

- 失败表现：P7“处理未完成项”只跳到更早页面，没有实际修复语言与内容颗粒度；用户看到动作成功感，数据却未变化。
- 根因：导航动作被当作修复动作，前端没有调用质量修复服务、排队重生成并跟踪进度。
- 永久规则：带“处理/修复/重新生成”语义的动作必须产生可验证业务写入或异步任务，并显示进度、失败原因和可重试状态；若只能导航，文案必须明确为“前往处理”。测试要断言请求、状态变化、刷新保持和最终正文，而非只断言页面跳转。

## 2026-08-24：项目内资源 URL 不是可跨任务复制的权威数据

- 失败表现：复制或迁移后的玩法审核模型仍保存旧 job 的 `/artifacts/<jobId>/frames/<frameId>`，文本和规则正常，但正式页面的参考图批量 404；只测试《一路狂飙》当前任务会漏掉该问题。
- 根因：把可由 `current jobId + frameId` 确定性重建的派生 URL 当成持久事实复制，加载旧模型时又没有重新绑定任务上下文。
- 永久规则：跨任务复制、迁移、恢复和模型加载都必须按当前 job 的 frame 索引重建资源 URL；发布前递归扫描所有图片引用，拒绝 foreign jobId、404、`naturalWidth=0` 和非当前任务资源。测试固定包含“旧任务模型复制到新 job”的负例。

## 2026-08-24：修复完整任务不等于修复新建或失败任务

- 失败表现：《一路狂飙》已有完整 gameplay model 时 P1–P7 可进入，角色创建等首次生成失败的任务却被门禁锁死，无法从 P1 恢复；项目特定成功掩盖了状态机缺口。
- 根因：路由与启用条件只覆盖 happy path，把 `generation=failed && model absent` 当成不可恢复终态，而不是保留素材与重新生成入口的可恢复状态。
- 永久规则：每次工作流修复必须建立状态矩阵，至少覆盖 completed、pending、failed-with-model、failed-without-model、legacy/migrated 和 new job；失败状态只阻断无依据的确认/导出，不能剥夺素材、目录、配置、重试和工作台恢复入口。

## 2026-08-24：深层编辑动作必须原子打开完整可见路径

- 失败表现：P4“编辑规则”只展开内层规则编辑器，外层“策划确认与修改”仍折叠，DOM 中编辑器存在但用户看不见，按钮因此表现为失效。
- 根因：动作只修改目标节点，没有把祖先 disclosure、滚动位置和焦点视为同一个导航事务。
- 永久规则：任何“编辑/定位/处理未完成项”都要原子完成祖先展开、目标展开、滚动、焦点和 URL/状态同步；测试必须断言目标真实可见、获得焦点且刷新后路由合理，不能只断言 `open=true` 或节点存在。

## 2026-08-24：保存成功必须验证业务写请求，不能被 UI 状态请求冒充

- 失败表现：页面反复提示“当前环节保存失败，内容仍已保留”，或测试看到若干 200 请求就认为保存成功，但实际业务保存可能未发出、命中错误 job/revision，或只有 UI-state POST 成功。
- 根因：业务保存、界面状态持久化和错误提示共用模糊状态；无变化保存、409 revision、服务异常与网络失败没有可区分诊断。
- 永久规则：保存用例必须锁定唯一业务 endpoint、job/object ID、expectedRevision、请求次数、响应和重载后的数据；UI-state 请求不得计为业务保存。无变化保存不失效审核；失败时保留编辑内容、展示可操作原因并允许幂等重试。

## 2026-08-24：部署动作完成不等于正式地址已替换

- 失败表现：本地 payload 已更新、远端服务显示 running，但正式地址仍加载旧 `ux/gameplay` 版本；RDP 复用会话、发布程序未启动、凭据失效或安全确认假设会让部署状态被误判。
- 根因：部署流程把“包已准备”“EXE 可能启动”“服务运行”和“正式站点消费新静态资源”混为一项，并依据推测描述远程界面。
- 永久规则：部署状态分为 package-ready、remote-copy-complete、service-restarted、live-version-verified、live-QA-passed 五个独立阶段。只有正式 URL 回读版本、资源哈希/manifest、关键 API 与浏览器全流程均通过才可报上线；凭据或 RDP 阻断必须如实报告，不猜密码、不虚构弹窗、不把 service running 当发布成功。

## 2026-08-24：网页发布验收必须从用户可见行为和像素反向验证

- 失败表现：按钮在 DOM 中但被折叠层遮住、文字卡片重叠、竖图被方形容器裁切、图片延迟加载被误判为空白，或者跳转只改面板没有同步 URL/刷新状态。
- 根因：自动化偏重元素存在和接口返回，缺少真实点击、稳定等待、布局几何、图片解码、控制台/网络和刷新返回验证。
- 永久规则：发布自检固定覆盖真实点击 P1–P7、内部编辑/保存/继续按钮、URL 与历史记录、刷新恢复、控制台、失败请求、图片 `complete/naturalWidth`、文字/容器边界和桌面多宽度截图。布局问题必须用截图与几何断言双证据；图片按源比例 `contain`，不得用正方形裁切掩盖适配问题。

## 2026-08-24：一次修复必须形成跨项目回归资产

- 用户指出的单点问题要上升为可复用不变量：当前任务复现用例、跨任务负例、新建隔离任务用例、旧数据迁移用例和正式地址冒烟共同组成防复发链。
- 只写聊天结论或记忆不算底层逻辑完成；对应问题必须进入公共实现、自动测试、发布检查或 QA 用例。若当轮因部署/凭据阻断无法完成正式验证，状态保持未闭环并在后续发布前强制补测。

## 2026-08-24：压缩后的 Rule Projection 不能替代完整执行案

- 失败表现：结构化 Rule、Guard 和 Feedback Trace 全部正确，但直接把稀疏 PublicationProjection 当成完整正文后，载具栏位、武器获取、首领阶段、结算流程等已确认执行内容丢失，文档看似安全却不可交付。
- 永久规则：Final 必须以 Approved Rule/Fact/Narrative/Feedback 的全局恢复结果重建 Mechanic Flow；安全压缩只能移除重复、无价值派生句和越权推断，不能把有执行价值的已确认内容一起删除。

## 2026-08-24：保留飞书资产也必须审计资产中的旧规则

- 失败表现：原生表格和流程图被正确保留，但旧表格中仍可能含等概率、无放回、公式、固定奖励或隐藏优先级；“保留原生资产”本身不等于内容安全。
- 永久规则：所有保留表格与图表都要经过与正文同一套 Final Pollution Guard；不安全表格应以 Guard-safe 原生表格替换，不能只检查块类型和数量。

## 2026-08-24：飞书图表位置属于正文语义，不是附录排版

- 失败表现：图表集中放到专门区域，或玩法概述/单局流程被移动到文档末尾，会让完整内容仍然难以阅读，并破坏策划执行顺序。
- 永久规则：玩法概述和单局流程固定在正文最前；表格和流程图必须紧邻其解释的机制章节。图表数量、类型、语义锚点和远端顺序都需要回读验证。
- 本文档中根标题不能作为普通 `block_move_after` 锚点；调整顶部顺序时，应重建顶层 H2 锚点并移动对应块。

## 2026-08-24：SVN 首次导入与后续增量同步是两种流程

- TortoiseSVN 的首次 Import 可建立 `AI/trunk/ai_gamedesigntool`；但后续版本不得继续用 Import 冒充增量提交。
- 后续同步必须从 Git HEAD 构建可复现包，进入受控 SVN working copy，再 add/delete/commit；依赖只允许白名单根，缓存和凭证必须过滤。

## 2026-08-21：领域 Probe 存在不等于生产闭环

- 失败风险：只有 `run_targeted_temporal_probe` 和持久化函数，但 `_generate_gameplay_review` 在 model build 后直接保存，真实上传任务永远不会执行 Probe。
- 失败风险：旧 request builder 只认 `status=unresolved`，而 v2 Schema Gap 使用 `status=open`；仅连接服务仍会得到零请求。通用解法是读取 Gap 显式声明字段，不是新增玩法词或 `if/else` 分类。
- 失败风险：每持久化一个 Probe 就重建一次 projection，会把有界两阶段编排退化成 N 次重建。批内持久化要保留 revision/undo，但只在批尾统一 rebuild 一次。

## 2026-08-21：Temporal Evidence 权威与兼容

- 不要把 screen-space bbox delta 当成 gameplay movement；必须分别保存 visual motion、reference-frame representation 和 reviewed gameplay rule。
- 新增 review-model 字段时，validator 必须兼容字段缺失的历史任务；只读 Final Preview 可能直接验证旧模型而不先执行迁移。
- Closure 只能由 confirmed/approved Rule 满足；把 unreviewed RuleCandidate 纳入 intent 集会造成视频观察自动关闭 Schema。
- Exhausted Probe 必须绑定 Evidence revision；普通 projection rebuild 不应重新执行搜索。

## 2026-08-21：停用画板不能只隐藏最终输出

- 失败风险：只让 renderer 不输出 UE/竞品画板，旧 `ue_flow` 路由、completion check、competitor mutation gate、accepted preview tab 或 legacy embed anchor 仍会阻塞流程或产生空白页面。
- 永久规则：画板载体变更必须同时覆盖工作流路由、生成选择、预览摘要、完成度、Final、飞书、accepted API、历史深链与旧 anchor 兼容；底层数据可保留，但不得继续影响当前主链。

## 2026-08-21：接口接收 Rule/Relation 不等于已经参与激活

- 失败风险：`activate_responsibilities` 虽然接收 `rules` 与 `relations`，若内部仍只检查 Evidence Signal，就会让接口形状掩盖实际能力缺口。
- 永久规则：每种激活来源都必须有独立 RED 测试、显式声明式 contract 与 provenance 输出；Approved Rule 和 Relation clause 同时声明时必须共同满足，未批准 Rule 不得激活。
- 执行维度归属写在 JSON Responsibility 的 `planningDimensions`，禁止在 Python 里按 Responsibility 名称或玩法类型维护映射表。

## 2026-08-21：可检测 Pattern 不等于完整知识图谱节点

- 失败风险：只新增 Pattern、Signal 和 Benchmark，未补 L1/L2 contains、L4 may_activate 或 shared concept 边时，Pattern 虽能命中，却不能形成自然层级或跨 Pattern 组合。
- 永久规则：validator 必须拒绝未声明 Signal、孤立 Pattern、孤立 Responsibility 和无 shared concept 的 Pattern；迁移测试必须加载真实 JSON 执行该完整性门禁。

## 2026-08-20 Mechanic 图谱不能用标签枚举和分支代码冒充迁移能力

- 失败风险：把 Mechanic 做成词典或按品类写 `if/else`，只能识别标签，不能表达同一场景中的多机制组合、动态职责和跨系统关系；扩充品类还会不断增加项目特例。
- 永久规则：Pattern、Signal、Responsibility 和共享概念全部进入版本化 JSON；Python 只实现通用信号契约、图查询、组合与缺口派生。新增玩法只能增加图数据和 Benchmark，不得增加玩法特定分支。
- 品类、Taxonomy 命中和 Pattern 完整度都不是存在证据。Pattern 可声明候选职责，但每个可选职责必须有自己的激活信号；无信号时 dormant，不能制造 Gap 或虚高 Recall。
- 多 Pattern 只有通过共享 Entity / Resource / State / Event / Flow 才形成当前项目结构；仅返回标签列表不能支持 RuleChain、自然 Planning Hierarchy 或跨系统缺口发现。

## 2026-08-20 飞书白板节点存在不代表文字可见

- 飞书 raw node 的写入顺序会影响远端 z-order；在本次 UE 修复中，后写的白色页面底板覆盖了先前文字与编号，导致本地结构完整而远端看似空白。
- 永久规则：按远端实际层级规则写入，背景/容器先规划但在需要时后置到低层，内容节点保持高层；发布后必须导出远端 preview 并回读 raw，逐页确认截图、1/2/3/4 标记、组件说明和连线都真实可见。

## 2026-08-20 原子标题正确仍可能 Owner 错位

- 失败表现：拆掉“X与X”复合标题后，目录看起来更干净，但把伤害统计放进战斗规则、把武器伤害公式留在武器章，仍与权威逐章审计不一致。
- 根因：只做标题词法检查，没有同时核对 GVE16 第一手标题树、当前项目自然层级和每段 Primary Owner。
- 永久规则：标题验收必须同时检查“名称是否原子、内容是否同责、Owner 是否正确、章节顺序是否符合阅读链”；任何一项失败都不能通过。
- 已沉淀为 `skills/gve16-publication-acceptance/SKILL.md`。

## 2026-08-20 最终正文必须从用户可见交付反向验收

- 内部 Closure、测试、Review Layer、raw node 或关键词命中都不能证明正文完成；必须从网页/飞书中的最终句子、表格、图示开始，反查 Approved Data 与 Source。
- 正文的典型假完成包括：完整规则被 summary/fallback 覆盖、同一句复制到多个 Owner、参数只进表不进消费规则、图示集中在文末而没有紧邻对应正文、相关关键词冒充原子问题答案。
- 永久规避：逐章逐段比较 GVE16 暴露的执行问题，形成项目自己的答案；正文主要由 Approved Structured Rules 确定性投影，记录真实来源占比，并对 Unsupported Claim、Wrong Owner、Generic Fallback、Duplicate Primary Rule、Satisfaction False Positive 和 Publication Loss 建硬门禁。

## 2026-08-20 飞书远端画板不能用本地 SVG 或节点存在代替验收

- 飞书可能保留 SVG 结构却剥离其中的栅格图片；Section、image shell 或媒体映射存在仍可能让用户看到空白。
- 红圈和数字分成不同节点会在远端缩放后漂移；自由填写坐标会让编号落在与说明不对应的区域；标题贴近画布顶边会被远端导出裁切。
- 永久规避：截图使用 whiteboard scope token，圆形与数字合成一个居中节点，坐标由组件 targetBox 推导；结构写入先于媒体，发布后同时导出 preview 与 raw，检查非零图片、编号锚点、标题安全区、连线方向和所有遮挡。

## 2026-08-18 Human Preview 分组不能反向覆盖知识树

- 为检查文档质量临时形成的阅读分组，可能比真正的 System/Subsystem 层级更扁平；把它们直接迁移为网页目录会把 presentation grouping 误当 domain model。
- 永久规避：目录始终从 Evidence、MechanicScope 与 owner resolution 正向生成；Human Preview 只消费目录，不能成为目录事实源。
- Entity owner、规则 owner 与章节 owner 必须分开，否则会出现“载具栏位/武器栏位”重复定义，以及“结算页显示什么就归结算”的展示位置污染。

## 2026-08-12 图解有箭头不等于策划语义正确

- 失败表现：通用生成器把首领生命、载具攻击力、候选数量、通关时间等参数串成流程，技术上存在矩形和箭头，却没有玩家操作、系统处理、分支或循环。
- 根因：图解生成读取参数表而非 `plannerSections.normalFlow/keyRules`；质量门禁只检查 SVG 图元，没有检查业务语义。
- 规避办法：策划语义图从已确认流程提取动作、处理、判断、分支、循环和结果；参数只做注释。人工编排图标记 curated，通用生成器不得覆盖；用户判退后立即停止审核并退回重修。

## 2026-08-12 图解失效更新不能新增重复图或降级旧图

- 失败表现：5张过期图点击批量更新后没有刷新原图，反而新增7张单章节图；随后候选 SVG 只有矩形文字，覆盖了带判断和回路的旧图。
- 根因：自动生成仅按“完整章节组合+类型”去重，无法识别跨章节图已经覆盖单章；刷新器也没有策划图保护和候选质量比较。
- 规避办法：过期图原位重建并保留 ID/章节绑定；跨章节覆盖参与去重；更新前后核对有效图数量、ID、版本和关系密度；低质量候选不得覆盖上一版合格图。

## 2026-08-12 图解三栏未绑定同一 ID 会反复通过错误对象

- 失败表现：用户切换左侧章节并逐项点通过，统计仍是2/6；后端 revision 连续增加，但多次写入同一张 `GDI-101`。
- 根因：左侧导航只隐藏/显示中间卡片，没有更新右侧审核 detail；右侧按钮闭包始终绑定初始图解。
- 规避办法：左侧章节、中间图解、右侧审核对象绑定同一图解 ID；切换章节时右侧选择第一张未决图。自动测试必须断言提交的 ID；验收同时检查后端逐图状态、6/6汇总、P6跳转和刷新恢复。

## 2026-08-12 状态颜色不能脱离后端真实状态

- 失败表现：待审核图在左侧也显示绿色圆点，使用户误以为已经通过。
- 根因：导航圆点样式固定为绿色，没有读取图解 status。
- 规避办法：open=橙色“待审核”、stale=橙色“需更新”、reviewed=绿色“已通过”；汇总、百分比和路由必须与后端逐图状态同源。

## 2026-08-11 验收说明不能替代真实页面证据

- 曾在 P1 实际没有显示决策卡时就给出“应看到决策卡”的验收说明，暴露出实现、用例确认、自检和证据之间没有硬门禁。
- 规避办法：每阶段先把可执行用例交给用户确认，再逐条真实自检并截图；失败立即退回修复，造数后恢复正式任务，最后展示证据并等待用户明确验收。自动化测试和 DOM 断言不得冒充截图，未触发分支不得声称已验证。

## 2026-08-11 P7 与飞书必须在所有摘要层级同源

- 阶段 2 自检发现：章节正文虽已优先读取 `plannerSections.summary`，但 P7 文档概述的“核心玩法一句话”仍读取历史 `chapter.summary`；同时 P7 把“怎么验证”放在“特殊情况”之前，与飞书正文顺序不一致。
- 规避办法：不仅比较章节主体，还要截图检查文档概述、目录、章节和旁栏等所有重复消费点；P7 与飞书统一优先使用策划确认摘要。后台仍检查流程、规则、例外和验收，但最终正文不把这些维度固化成标题或统一顺序。

## 2026-08-11 后台审核维度不能变成固定正文模板

- 阶段 2 第一轮把“正常怎么玩、关键规则、特殊情况、怎么验证、参数、公式”等后台检查项直接渲染成每章标题，并在隔离截图中泄漏“阶段2、隔离验收”等测试术语；配置字段还被正文表和关联表重复展示。
- 阶段 2 最终验收确认：短机制应合并在一个业务大章节内，段首名称与正文合成一句；摘要和单条补充规则不得重复拆成项目符号。“机制”“状态管理”等不增加信息的尾词可在合并展示时省略。复杂机制只有在真实内容量、顺序、配置或公式足够时才保留独立层级。
- 规避办法：正文只保留机制专属标题和自然段；有真实顺序才用列表，配置只保留一张已审核表，具名公式直接嵌入正文，通用验收项不发布。任何 QA 标签只能放在截图外层证据横幅，不能进入文档内容。

## 2026-08-04 谨慎措辞不能整句降级成未知

- 过滤器曾因为句子含“可能、推测、待确认”就把整句放进黄色注记，导致交互交付物出现十条无决策价值的“未知待确认”；这不是视觉模型能力不足，而是后处理误伤。
- 规避办法：按分句提取明确画面事实，删除纯猜测；只有影响流程或规则且需要策划选择的问题才生成黄色注记。环节应汇总全部代表图，解析失败的空环节并入相邻有效环节并保留原图。

## 2026-08-04 不得把当前素材结构固化为通用模板

- 当前素材拆成“战斗与关卡、局内成长”只是一次识别结果；把它写死为全局分类会让无首领、无武器或非战斗玩法产生错误目录。
- 规避办法：AI 先基于素材提出目录建议，策划在前置目录环节确认；所有下游输出读取确认后的结构。

## 2026-08-04 代码已修改但页面仍旧可能是启动路径问题

- 服务曾优先加载运行目录中的旧模块，导致测试和源码正确但浏览器仍显示旧的单一“玩法系统”。
- 规避办法：启动时项目源码路径必须排在依赖路径之前；修复后必须通过真实页面 DOM 或预览结构复核，不能只看单元测试。

## 2026-08-04 交互事实不能直接拼成玩法规则

- 将“进入、操作、反馈、结果”直接拼成段落会产生重叠、阅读负担，并把鼠标位置、弹窗表现等证据误当成玩法规则。
- 规避办法：白色卡片使用已确认的分条规则；不确定内容进入黄色注记；玩法摘要与交互证据分层保存。

## 2026-08-04 视觉模型失败必须一次性定位完整链路

- 反复显示“请求失败、超时、内容不符合要求”但不保留诊断，会让用户只能重复点击，任务还可能自动消失。
- 规避办法：分别记录请求、响应解析、质量校验、持久化和前端恢复状态；失败保留素材、进度、明确原因和可重试入口。

## 2026-08-04 交互策划草图不能用玩法系统树代替

- 曾把玩法系统、模块和规则卡直接画成交互交付物，虽然内容可读，却与 GVE16 样例的“页面截图 + 页面规格说明”结构、颗粒度和阅读顺序完全不同。
- 2026-08-20 再次发现另一种退化：把15张状态截图压成6张机制摘要卡，导致普通战斗、返回战斗、刷新后候选、终极词条、首领切入等页面状态在策划草图中失去独立位置。永久规则：策划草图必须是完整页面/弹窗/状态地图；每个已观察状态使用一张代表截图和邻接“界面构成”，再以已观察或已批准的状态衔接连接。UE 的判断/分支菱形不得复制到策划草图。
- 规避办法：交互画板按页面或页面状态组织，截图保持原始比例，右侧完整列出动态页面分组；玩法系统分类仅进入玩法目录和正文。修复时必须整体替换数据模型和布局，不能只调整换行或箭头。

## 2026-08-04 页面规格画板必须用真实任务和发布链验收

- 单元测试人工补齐顶层尺寸时，可能掩盖真实任务只在 `frame.structure` 保存宽高；同一帧复用也可能被发布器按 frame id 过早去重，造成后续图片节点缺图。
- 规避办法：比例测试必须覆盖真实持久化形态、互质大尺寸和 `imagePath` 恢复；发布测试必须覆盖“同一帧上传一次、多个节点全部获得 token”；连线测试检查完整线段与页面、正文、图片和黄色注记矩形是否相交。

## 2026-08-05 先确认结构，再生成细节

- 视觉模型直接从截图生成完整玩法章节时，容易把样例目录套入新素材，或者在策划调整目录后重新洗牌。
- 规避办法：把生成拆成两段；第一段只识别动态系统层级并让策划两次确认，第二段逐机制读取对应证据补全规则，且系统名称、章节名称和编号以确认结果为硬约束。

## 2026-08-05 同等颗粒度不等于同一套字段

- 用战斗模板衡量所有玩法，会让经营、合成、建造、解谜或未知新玩法被迫出现不适用的武器、敌人和伤害公式。
- 规避办法：共享“规则可执行、数值可配置、结果可验收”的完整度契约；公式、参数、概率、资源流和空间规则按机制实际需要出现。任何公式或配置字段没有素材或参考文档依据时不得作为确定事实发布。

## 2026-08-05 结构识别依据不能直接成为玩法章节说明

- 玩法结构阶段曾把模型输出的“画面依据”同时写入 `mechanism.description`、目录摘要和章节说明，导致“画面显示、小地图黄线、虚拟摇杆、绿色血条、具体截图数字”等看图描述冒充玩法规则；已确认章节又跳过迁移，使错误长期保留。
- 规避办法：结构阶段的画面依据只进入证据层；策划可见摘要必须重新抽象为机制目的、规则过程、状态变化和结果。迁移只重写自动生成或明显受污染的文本，策划手工修改内容必须带来源标记并保留。
- 每次生成前执行主策输入检查，每次生成后执行策划可见文案审计；出现画面布局词、内部英文、空泛“某某的玩法规则”或缺少系统层级时直接阻断。

## 2026-08-06 稳定性不能只依赖低温度和重复调用

- 同一素材重复调用视觉模型仍可能改变系统拆分和策划颗粒度；模型失败后使用简单兜底还会把低水平结果伪装成成功。
- 规避办法：按素材内容、顺序、模型和提示词版本生成指纹；只缓存通过主策质量门禁的结果；冻结人工确认内容；不合格候选不得覆盖上一次合格版本。
- 复用历史高质量样例时必须先脱敏为结构计数与模块开关；原始玩法事实不能进入新任务提示词。

## 2026-08-06 已确认目录不能冻结错误的自动摘要

- “目录已确认”只应锁定策划确认的标题、顺序和手工文案；自动生成且已被新证据纠正的章节说明必须允许刷新，否则错误会长期回流。
- 目录文本在点击确认前必须强制提交仍处于编辑状态的输入，不能只依赖失焦事件；回归测试必须覆盖“编辑后直接确认”。

## 2026-08-06 图解、表格和交互预览必须按业务阶段隔离

- 把章节摘要或公式包装成节点图不会增加信息量，反而增加审核负担；不能仅凭机制名称决定生成图解。
- 规避办法：自动生成前检查是否存在至少两个可连结的真实规则字段或跨章节关系；公式一律回到正文公式块，普通参数回到表格。旧的纯文字/公式图解在再次整理时自动删除，并将章节标记为“无图解”。

- 机制类型为通用占位值时，不能直接判定“无图解”；应根据策划文案识别空间关系、状态流程、效果链、概率或公式结构。
- 参数与公式没有明确来源时只能标为“待策划确认”或既有可信度，禁止默认写成“当前素材”。
- 玩法自动补全的失败提示只能出现在玩法生成或最终预览阶段，不得污染交互交付物；交互预览打开后应直接滚动到真实画板内容。

- 禁止以空的模型配置启动玩法章节或最终预览的自动补全。目录确认必须向后端传递当前模型配置；`detail_generation_pending` 不得冒充“已完成”。如果密钥缺失，必须在发起任务前打开可见的模型设置，保留原任务并提供“保存配置并返回当前工作台”的恢复路径。
- 玩法图解不得用 `scope`、“待确认”或空字段填充公式、参数和算例。只有存在真实公式时才生成公式图；状态变化优先使用效果链；无有效结构时明确标记“无图解”。内部字段名必须转换为策划熟悉的中文。
## 2026-08-06 代表截图不能充当素材覆盖清单

- 只用 `representativeFrames` 渲染和校验，会导致同一页面的补充截图没有独立说明框，并在旧任务迁移、页面合并或代表截图替换时出现素材无归属。
- 规避办法：页面另设完整的 `sourceFrameIds`，素材保存 `stageId` 与 `materialRole`；页面合并和代表截图替换必须原子迁移归属，接口读取旧任务时运行并持久化回填。
- 自动测试必须同时覆盖：全部素材恰好一次归属、重复素材标记、互斥分支一次性切换，以及页面合并和代表截图替换后的完整性。

## 2026-08-06 无变化保存不得打回审核状态

- 编辑器若无差异也提交完整页面操作，会触发确认失效，使后续玩法审核按钮重新禁用。
- 规避办法：前端先比较页面名称、进入状态和四步说明，只提交真正变化的字段；无变化保存只显示成功反馈，不修改版本和确认状态。

## 2026-08-06 旧质量字段不得遮挡已确认工作台

- 新版交互审核已经确认页面目标和参考画面后，旧版五段小循环仍可能保留“待确认”。若质量检查只读取旧字段，服务重启或重新加载时会把完整任务误判为 `NO_QUALIFIED_STAGE`，看起来像数据被清空。
- 规避办法：质量门禁同时识别当前审核结构；已确认、页面目标明确且有参考画面的环节视为合格。未确认的低质量分析仍按原规则拦截，并用正反向回归测试锁定。

## 2026-08-10 对齐飞书颗粒度不能只对齐目录

- 样例的深度来自证据链：截图和视频证明可见状态与顺序，参考文档证明隐藏规则与生命周期，配置表证明字段和数值，会议纪要证明端侧职责与退出重进。
- 规避办法：发布前按“内容清单、配置字段、执行顺序、公式、异常边界、生命周期”逐项比较；有证据却缺少任何一类都阻止发布。不得把 GVE16 或 GVE5 的具体系统目录固化到其他玩法。

## 2026-08-11 裸未知项不是可审核内容

- 让策划编辑一段“待确认”文字或只选择“暂时无法确定”，没有提供真实决策空间，也无法可靠同步到下游交付物。
- 规避办法：只有至少两种合理解释时才创建结构化卡片；卡片携带选项、推荐依据、选择限制、影响范围和自填入口。应用结果写入规范规则数据，跳过只改变卡片状态，绝不能提升为正式结论。

## 2026-08-11 参数命名必须保留机制语境

- 飞书样例不是先建立通用字段字典总表，而是在行为说明后就近逐行映射“业务名 → 配置表/字段名”，再由配置表承载值、单位和范围，并在机制结尾说明不可逆、保存或重置范围。
- 规避办法：按“行为正文 → 就近命名映射 → 必要的配置表 → 生命周期”组织。只有参考文档、配置表或策划决定提供权威名称时才写正式表名和字段名；只有截图证据时写“建议程序字段名（待程序/配置表确认）”。不得用集中字段字典总表替代这四种职责。

## 2026-08-12 表格完整不等于属性正文达到样例颗粒度

- 失败表现：字段在表格中齐全，但正文没有解释属性参与什么判断、何时读取、怎样影响结果。
- 根因：门禁把参数表视为配置维度完成，没有单独检查正式正文的属性解释。
- 规避办法：使用 `attributeNarrative` 审核轴，只读取正文属性载体；表格不能满足该轴。

## 2026-08-12 审核说明会伪装成图解补充并污染正文

- 失败表现：图后出现“流程图只确定……仍由决策卡确认”“不从流程图推断”等无研发价值的句子。
- 根因：图解 `placement.followUp` 被发布，但旧语言门禁只检查章节正文。
- 规避办法：语言审计同时检查正文和图解说明，以 `LANGUAGE_REVIEW_META` 阻断审核过程、证据能力和决策卡状态术语。

## 2026-08-12 全局输入样式会破坏决策卡单选布局

- 失败表现：radio 继承 `width:100%`，圆圈占满整行，文本被推到右侧并在短词中间换行。
- 规避办法：radio/checkbox 固定为 16px，文本 `flex:1` 且短项不换行；真实浏览器检查 computed style 和截图。

# 2026-08-13：失败任务重试必须重新验证模型凭据

- 失败表现：用户已经配置过模型，但浏览器换会话或 Key 未回填后点击“重试任务”，前端仍直接请求重试接口；后端收到空 Key 后退化为无模型分析，最终显示“0 个请求失败、0 个代表帧达标”，容易被误判为模型内容质量问题。
- 根因：新任务入口有 `hasVisionModelConfig` 门禁，失败任务重试入口没有复用同一门禁；模型地址与模型名可以从任务恢复，但出于安全约束，API Key 不会写入任务文件，因此不能依赖历史任务自动补齐密钥。
- 永久规则：所有会触发模型调用的入口（新建、重试、整片重解读、局部重解读、自动补全）都必须在提交前验证当前浏览器或服务端确实存在有效凭据；缺少 Key 时只展开模型设置并明确提示，不得创建请求、不得进入无模型占位分析、不得把结果表述为内容质量不合格。
- 验收要求：回归用例必须断言缺少 Key 时网络请求数为 0、设置面板展开、提示可操作；补齐 Key 后再断言重试沿用原任务 ID 和已保留素材，且 `analysisSummary.modelEnabled=true`、实际模型请求数大于 0。

# 2026-08-13：交付卡片必须区分进入审核与生成文档

- 失败表现：交付摘要卡片只有“生成完整策划案”，用户无法从当前任务直接回到 P1–P7 工作台，容易把“生成文档”和“继续审核”误认为同一动作。
- 永久规则：卡片同时提供“进入工作台”和“生成完整策划案”；前者恢复当前任务及保存的工作台阶段，后者只负责生成交付内容。没有审核模型时保留入口并给出明确前置条件，禁止跳到其他历史任务或打开空白工作台。
# 2026-08-13：玩法目录不能把异质机制压进一个大章节

- 失败表现：目录把 19 个具体机制全部归入“城市收购”，其中同时包含战斗触发、人员配置、增益、收购消耗、特殊建筑和结算反馈，章节名已经无法代表内部内容。
- 根因：生成器直接把最显眼或出现频率最高的功能名当作顶层玩法系统，没有先做系统边界归纳，也没有检查机制之间的目标、对象、资源、状态机和生命周期差异。
- 永久规则：先识别大机制，再生成具体章节；不同玩家目标、操作对象、资源流、状态机、生命周期、实现职责或独立验收结果应拆为不同系统。同一闭环且共享对象、资源和生命周期的连续步骤才允许合并。
- 反向约束：不设固定系统数量，不得为凑层级硬拆；但出现大量异质机制仍只有一个顶层系统时必须判定目录过度扁平并重新分类。

# 2026-08-13：同一页面的内部步骤不能套用跨页面跳转

- 失败表现：P1 第一步确认后，后端已把目录推进到 `mechanisms`，前端却仍执行进入 `flow` 的旧跳转；路由保护虽可能拦回 P1，但 URL、滚动位置和用户看到的步骤不一致，表现为按钮没有进入第二步。
- 根因：确认回调没有读取接口返回的 `structurePhase`，把“第一步确认”和“P1 最终确认”共用了一条无条件跨页跳转。
- 永久规则：多阶段页面必须按服务端返回状态分支。P1 `systems → mechanisms` 时留在本页、URL 保持 `ui=gameplay_directory`、画布回顶；只有目录最终确认后才进入交互审核。
- 测试要求：同时验证模型阶段、可见页面、URL 和滚动位置，禁止只测后端状态或只测顶栏阶段。

# 2026-08-13：初始化恢复不能覆盖用户刚选择的阶段

- 失败表现：从 `ui=final_preview` 深链进入后立即点击 P1，页面先显示 P1，等规范模型同步完成又被拉回 P7；常规“加载完成后再点击”测试无法发现。
- 根因：初始化函数在异步请求前缓存了 URL 阶段，请求结束后无条件重新应用，没有判断等待期间是否发生了更新的用户导航。
- 永久规则：启动异步恢复前记录导航意图版本；只有版本保持不变时才允许重放初始 URL。浏览器验收必须包含“冷启动后立即点击其他阶段，并等待全部请求结束”的竞态场景。
- 补充规则：不仅 URL 重放需要版本保护，规范模型和玩法模型的 `rebuild` 也必须恢复等待期间用户最新选择的页面；刷新模型不能等同于自动推进工作流。
- 补充规则：历史任务响应已携带玩法模型时，要先同步初始化玩法工作区再启用 P4–P7。只根据嵌套模型存在就提前放开按钮，会出现目标页空白并被路由器拉回 P3。

# 2026-08-13：未完成入口不能复用固定返回页

- 失败表现：P7 显示“处理未完成项”，但无论真实缺口属于交互、规则、图解还是参数，点击后都固定返回 P6。
- 根因：未完成动作与“返回修改”共用 `onBack`，没有读取规范模型的首个阻塞阶段。
- 永久规则：保留两个独立回调；“返回修改”执行约定的固定编辑入口，“处理未完成项”调用统一路由器定位首个真实阻塞项，并同步可见页面、URL 与持久化状态。

# 2026-08-13：跨页推进不能只切换可见面板

- 失败表现：P3→P4、P5→P6、P6→P7 等“继续/进入下一步”按钮点击后画面会变化，但 `ui` URL 和持久化状态没有同步；刷新后返回旧页，迟到的异步审核响应还可能覆盖用户后续导航。
- 根因：顶部阶段导航与页面内部推进分别维护跳转代码，部分回调只调用 `setReviewWorkspaceView` 和重绘，没有执行 URL 同步、UI 状态保存及导航意图版本更新。
- 永久规则：所有显式跨页推进统一调用同一导航函数，原子执行“提升导航意图版本 → 选择实际可达页面 → 重绘 → 同步实际 `ui` → 持久化”。异步确认、图解审核和参数审核在请求开始时记录意图版本，返回后仅在版本未变化时自动前进。
- 测试要求：每条 P1→P7 主链按钮同时验证目标面板可见、URL 更新、刷新保持；另覆盖请求进行中点击其他阶段，旧响应不得把页面拉回。

# 2026-08-13：最后一环节也必须有可执行的下一步

- 失败表现：P2 前几个环节可以逐项确认，最后一个环节却因为不存在 `nextTransition` 被禁用，用户永远无法进入 P3。
- 永久规则：末环节与中间环节共用保存和确认动作；末环节显示“应用并进入交付物预览”，确认后先原子写入 `ui=interaction_preview`，再加载预览。

# 2026-08-13：跨域审核前必须持久化交接状态

- 失败表现：P3 只在浏览器切到 P4，却没有写入 `interactionHandoffConfirmed`；P4 最后一章通过后，规范路由又把用户拉回 P3。
- 永久规则：进入已有玩法审核时先调用后端交接接口并重新读取规范玩法模型，确认交接状态已落盘后再进入 P4。不能用本地页面切换冒充业务交接完成。

# 2026-08-13：上传数量上限必须前后端同源

- 失败表现：界面写“最多 50 张”，前端与后端仍硬编码 30 张；上传 42 张时按钮无说明地变灰。
- 永久规则：输入提示、前端校验、后端接口和图片落盘服务使用同一上限；固定覆盖 2、42、50、51 张边界，并用真实浏览器确认 42 张时“开始截图分析”可点击、51 张时显示明确原因。

# 2026-08-13：失败状态不能剥夺工作台入口

- 失败任务可能已经保留素材、部分合格分析或上一版 P1–P7 工作区；`failed` 只限制尚无依据的确认和导出动作，不能禁用或伪装“进入工作台”。
- 没有 `reviewModel` 的失败任务进入只读失败工作台，显示实际错误、保留素材数以及“配置模型、重试任务、返回素材”；有历史审核模型时继续恢复原工作区。
- 验收必须从失败任务深链真实点击“进入工作台”，核对 job、`ui=analysis_failed`、刷新恢复和三个恢复动作，不能只断言任务卡存在按钮。

# 2026-08-13：P5 章节选择必须是真实可恢复状态

- 失败表现：P5 点击第二个关联章节后右侧图解会切换，但选择只存在于当前 DOM；刷新后回到第一章。旧测试读取未参与渲染的 `selectedDiagramId=null`，刷新前后相等而误判通过。
- 永久规则：P5 关联章节选择复用玩法工作区的规范章节 ID，点击时立即持久化；重绘、模型重建和刷新均从该 ID 恢复。目标章节不存在时才回退第一项。
- 测试要求：必须断言点击后的章节 ID、`aria-current` 对应文本、刷新后的章节 ID 和高亮文本四者一致；禁止用恒定 `null`、默认首项或只看右侧内容作为通过依据。

# 2026-08-13：机械可跳转不等于主策工作流合理

- 失败表现：P1 同时出现两个新增章节入口；P4 页头和固定页底重复保存、通过；P6 每张表复制“上一节/下一节”，保存后又从同章多表变成单表；P7 把第一个未完成步骤高亮成当前页，并把参数审核排在图解审核前。
- 根因：组件分别实现自己的局部动作和状态展示，没有从“策划当前在审核什么、提交哪一个对象、下一步唯一是什么”统一设计；自动化只验证了点击与路由，没有验证认知一致性。
- 永久规则：同一动作单入口、同一对象单身份、同一完成度单数据源。列表审核保存后按对象 ID 原位恢复；总推进按钮只出现一次；P7 页面身份与未完成阻塞分开表达。
- 测试要求：除 URL、可见面板和刷新恢复外，统计同义按钮数量，核对每个写动作的目标 ID，验证同章多对象显示策略在操作前后不变化，并比较全局导航、P7 顶部和右侧状态的名称与顺序。

# 2026-08-13：历史章节缺少 claim ID 会伪装成“没有可合并/拆分内容”

- 失败表现：页面能显示历史章节正文，但合并、拆分面板没有可选内容；自动化若只检查按钮存在，会误判操作链通过。
- 根因：旧任务的章节保留了 claims，而目录 entry 的 `claimIds` 为空；部分旧 claim 本身也没有稳定 ID，目录无法建立章节归属。
- 永久规则：规范玩法模型加载时为缺 ID 的 claim 补稳定 ID；目录规范化时从同章 canonical claims 回填 `claimIds`，并保留真正未归属项。历史任务升级不能要求策划重新审核才能恢复编辑能力。
- 测试要求：浏览器必须真实打开合并/拆分选择面板并看到可选项；后端固定覆盖“章节有 claims、目录 ownership 为空”和“claim 缺 ID”两种旧数据。

# 2026-08-13：失败任务的模型配置不能丢失原任务路由

- 失败表现：失败工作台点击重试时，如果需要先展开模型配置，页面可能恢复到历史完成任务，或重试请求没有命中当前失败任务。
- 根因：配置面板打开与异步任务恢复分别修改 URL，没有保存失败页的 pending deep link。
- 永久规则：进入失败工作台时立即把失败任务 ID 与 `ui=analysis_failed` 写入当前 URL；打开模型配置前保存完整 pending URL，配置完成后原样恢复，再对同一任务发重试。
- 测试要求：从失败历史卡真实进入，填写 Key 后点击重试，断言仅 1 个 `/api/jobs/<失败ID>/retry` 请求；截图分别覆盖“仅打开失败工作台”和“重试已发起”，不得复用同一画面冒充两项。
- 2026-08-13 返回与异步保存：浏览器后退/前进、页内返回修改、返回素材、失败页返回和授权取消必须作为同一返回矩阵验证，检查目标页、任务 ID、当前对象及刷新恢复。用户检查已有 P5/P6/P7 成果时，单项保存只能留在当前页或向前，禁止按最早未完成门禁自动倒退。独立玩法接口的最新模型优先于交互模型内嵌旧副本，避免计数倒退和对象复位。大型 job.json 在 Windows 上原子替换时对短暂文件占用有限重试。
# 2026-08-17 Entity Graph 不能由 Presentation 反推

- 失败风险：按章节标题、UI 名称或表现句中的对象词直接建图，会把红色遮罩、跳字、边框等视觉概念提升为核心实体，并让表现证据反向定义逻辑关系。
- 永久规则：先用已批准领域声明和非 Presentation Approved Rule 构建核心图，图完成后才解析 `Presentation Rule → relatedEntityIds[]`；自动审计必须保证 Presentation 创建实体和支持核心关系的数量均为 0。

# 2026-08-17 共享 Entity 与证据仍不足以证明表现关联

- 失败风险：`attack_presentation` 过宽时，首领长血条会因共享怪物 Entity 和同批截图证据而错误关联到武器攻击或接触伤害。
- 永久规则：派生 VisualBlock → Logic 关联除共享 Entity 与证据链外，必须具备窄化后的结构化机制兼容关系和相同 owner chapter；宽泛 `attack_presentation` 与通用 `presentation_definition` 默认不派生关联。宁可 `relatedLogicRuleIds=[]`，不得制造伪连接。

# 2026-08-17 质量分必须防止目标替代

- 失败风险：只优化一 Rule 一句比例、段落长度或总分，会通过跨域强并、删 Rule、加空标题等方式制造 Goodhart 式假提升。
- 永久规则：Granularity 的 eligible Rule 分母固定在 MechanismBlock；跨 semantic domain 合并直接扣分，丢失 Rule 持续计入，标题必须由已有 mechanismSemantic 支撑。Explainability snapshot 同时锁定 score、ownerLayer、impact 和 minimalFix。
# 2026-08-17 模板覆盖不能冒充机制重建

- 仅检查 object/state/trigger/lifecycle 等模板槽位是否存在，会让无 Rule、无 Edge 的章节得到虚高推理分。机制深度必须奖励当前项目中有证据的有向关系，并对无 Approved Rule 模型设低上限。
- 状态名从 hypothesis 改成 derived_structure 不是推导依据；评分必须同时检查 `derivationJustified` 与 grounded edge evidence。

# 2026-08-17 整条 Rule 粗映射会丢失机制语义

- “怪物接触载具后造成伤害”若只映射为 attack trigger，会错误地把同一 Rule 明确支持的 damage result 标成 unresolved。必须先拆 condition + result，再分别确认节点并建立有向关系。
- `persists_until` 描述局部瞬时状态，不代表跨关卡持久化。生命周期评分只能读取明确的 initialize/save/reset，不得读取 transient duration。

# 2026-08-17 Gap 数量不能替代执行价值

- 从模板逐槽位发问会让无证据章节产生大量“规则是什么”式问题。新问题必须先绑定 grounded graph breakpoint，并能明确落到程序分支、QA 用例、参数契约或状态转换。
- 同义问题必须按 mechanic + decision semantic 合并；五个具体 breakpoint 问题应高于二十个换词泛问，不能按 Gap 数量加分。

# 2026-08-17 Grounded breakpoint 仍不等于值得问策划

- “自动前进与横向微调如何合成”虽然能绑定真实节点，但在没有冲突证据时只有一个自然理解，属于 common-sense deterministic，不应成为 P0。
- 同帧竞态、防重复提交等问题若没有交互或故障证据，属于实现基础能力或过度防御边界。DecisionWorthiness 必须位于 Planner-facing Language 之前。

# 2026-08-17 实现缺口不能自动升级为主策问题

- “无目标怎么办”“多目标按什么内部顺序”“下一次攻击何时执行”可能分别是实现默认或参数契约；仅因不同写法会产生代码分支或 QA Case，不足以进入 Planner Review。
- 静态截图可以证明对象、控件和某一时点状态，通常不能单独证明持续移动由自动路线还是玩家输入驱动。对时序/控制权结论必须检查动态证据；无法排除相反解释时路由 upstream conflict，而不是继续从该 Rule 推导 Gap。

# 2026-08-17 ReasoningGap 颗粒度不能直接成为主策颗粒度

- 入池、出池、满级移出与前置条件属于同一个候选资格 design lever；逐个 Graph breakpoint 展示会让主策重复处理同一结论。
- “空池”“不足三项”可能只是配置完整性保障；“选择后何时恢复战斗”在无特殊生命周期证据时是自然流程。先压缩再做显著性复核，避免把常识一起打包成看似高级的大问题。

# 2026-08-17 机制图深度不能替代游戏规则深度

- 多目标排序、无目标轮询、同帧冲突、输入合成和状态清理即使能形成完整技术因果图，也没有回答玩家怎么玩、成长和资源如何流转、关卡如何推进或胜负如何产生。
- Game Mechanic Depth 只奖励已确认的玩家可感知规则；30 条 Implementation Detail 与 0 条在该分数上必须等价。没有确认玩法规则的完整模板模型仍应低分。

# 2026-08-17 类型模板不能证明子机制存在

- `mechanicType=weapon` 不能自动推出解锁、替换、重复获取或栏位规则。模板条目只有获得 Rule、UI 结构或 Entity relationship 证据后，才能从探索候选提升到有效 scope。
- “接触伤害存在”能证明 damage mode 必须明确，但不能证明持续伤害存在；因此接触伤害间隔是 conditional gameplay parameter，而不是 Implementation Detail，也不能提前实例化为普通参数缺口。

# 2026-08-17 外部专业模板的广度不能成为项目事实

- Genre template、GDD checklist、经济公式族和 systems-designer matrix 擅长扩展探索空间，但它们越完整，越容易把不存在的机制实例化。外部 pattern 必须固定为 possible，状态提升权只属于当前项目证据。
- 配置 schema 和 ID 可提示系统关系，却不能证明解锁、掉落、奖励或成长机制存在；外部 benchmark、比例和公式常量不得作为项目默认值。

# 2026-08-19 无信号不等于不需要 Closure

- 失败模式：把“当前截图没看到”直接记成 N/A，会永久丢掉局外成长、关卡推进、奖励、体力、扫荡和活动生命周期等完整产品问题。
- 正确做法：先做 Scope Verification；若机制属于完整产品可能范围，继续 Evidence Probe、AI Design、Alternative 或 Human Product Decision。只有主策明确确认不存在才能关闭为 scope_confirmed_not_applicable。
- “不能复制 GVE16”只禁止复制答案，不允许删除 GVE16 暴露出的当前项目必答执行问题。

# 2026-08-19 综合摘要不能替代逐章逐句 Crosswalk

- 用户要求 GVE16 对齐时，重点是正文逐章逐句：比较每句的主语、条件、时点、动作、分支、结果、参数 Source/Consumer、Attribution 与 Reset。
- 目录评分、维度汇总和综合分只能作索引，不能冒充正文对照。
- 合并审计必须保留完整并集；去重不能删除原子 ID、逐句词义拆解或跨交付一致性矩阵。

# 2026-08-19 相关文字命中不能证明发布闭环

- Satisfaction Checker 必须检查原子答案，而不是关键词。例如“武器自动处理目标筛选”没有回答多个合法目标同时存在时的排序口径；“结果数量为3”没有回答三项是全部获得还是三选一。
- End-to-End Trace 的候选定位必须按载体分域：玩法规则优先正文，UE/PR 才可回退策划草图，P5 必须找真实 P5 交付，P6 必须找参数表。超长白板节点的偶然 bigram 命中必须降权。
- Final 来源占比必须区分完整文档与玩法规则正文，并防止短表格单元因为被长规则包含而继承 Approved Rule provenance。
- 飞书画板验收必须同时看预览和 raw。Section、connector、image token 都存在，但默认总览无法阅读，仍应判 visual satisfaction 失败。

# 2026-08-20 独立编号目录不等于正文自动编号

- 失败表现：渲染器在正文前生成“自动编号目录”，但实际章节仍是未编号标题；读者看到两套结构，飞书与网页开头也因此漂移。
- 根因：编号从标题扫描结果单独生成，没有包裹和承载真实章节正文；画板又由渲染器统一前置，绕过正文嵌入锚点。
- 永久规则：同一 canonical body 先写玩法概述，再用 BOARD/P5/P6 锚点确定图表位置；飞书原生 `seq=auto` 必须承载实际 H2 章节及其正文，不得生成独立编号索引。
- 验收要求：反向检查飞书开头先出现玩法概述；不存在“自动编号目录”；每个原生序号下有完整章节正文；网页与飞书的概述、章节和嵌入物顺序一致。

# 2026-08-20 RuleChain 有阶段不等于 Final 有 Owner

- 失败表现：RuleChain 已有首领进入、首领死亡和残敌清理，但 Final 的“怪物”只有普通怪物；首领仅以关卡流程中的两句转场存在，读者会判断内容缺失。
- 根因：章节组装按旧顶层模板保留普通怪物，却把 Boss 生命周期全部吸收到关卡 Owner，没有检查流程阶段与对象 Owner 的双向覆盖。
- 永久规则：先发布完整线性单局流程，再按出现顺序展开自然 Owner；流程中已证明存在的对象或阶段必须拥有可见章节。当前项目“怪物”固定由证据激活普通怪物和首领两个子章，不推广为其他项目模板。
- 验收要求：目录顺序能从进入挑战连续读到结算；怪物章同时出现普通怪物、首领；首领章回答 Entry、可见战斗信息、终止和残敌清理；详细规则只有一个 Primary Owner，流程章只作导航摘要。

# 2026-08-25 成功项目不能遮蔽缺失聚合根

- 失败表现：已有成功项目的 P1–P7 正常，但其他已有项目的 Gameplay Model 生成失败后，GET 500、P1 空白，P4–P7 直达路由不一致；新项目则没有 model 字段。
- 根因：把聚合根的存在性错绑到异步生成成功，又让读接口承担惰性写入；前端只判断对象是否存在，没有区分空容器的 lifecycle。
- 永久规则：交互模型建立后即建立 Gameplay Model；从未生成成功时，由 Approved Flow / State 投影稳定 ID、顺序、阶段、跳转和组件状态骨架，但绝不生成 Gameplay Rule；生成失败保留最后有效版本；GET 只读并在规范化失败时返回恢复骨架；重试同时接受 missing/required/failed；前端依赖显式 lifecycle，而非章节数。
- 页面能否打开取决于聚合 `/api/jobs/{id}`，不能用专用 `/gameplay-review-model` 返回 200 代替端到端通过。所有承载 Gameplay Model 的 GET 都必须在副本上规范化、失败时降级为骨架、永不因惰性迁移写盘或返回 500。
- 只显示 `generation_failed/failed` 不构成可恢复产品态。必须保存并展示 configuration/network/quality/system 四类原因、当前素材是否达到数量门槛、质量覆盖是否仍可能不足，以及用户下一步；刷新不得自动重试，显式重试必须重新排队并保留确定性骨架/最后有效版本。
- 页面导航不能伪装成重试操作：点击 P1、刷新或深链恢复只渲染失败原因与重试按钮，不得直接调用生成接口，否则用户看不到原因且会发生不可预期的 AI 消耗。
- 直达 URL 是状态的一部分：恢复视图时必须以 replace 同步 canonical URL，否则刷新、后退或异步 hydration 会把错误页面带回来。
- 测试必须是全局矩阵：已就绪旧项目必须能继续访问 P2/P4/P5/P6/P7，失败旧项目必须 200 且可重试，新项目必须在交互模型建立后得到 Approved Flow / State skeleton，重生成失败必须保留最后有效版本；截图序列与视频输入都必须覆盖，同时检查截图布局、URL、控制台和网络失败。

# 2026-08-25 生成失败不等于已有工作区失效

- 失败表现：Gameplay 生成失败后，路由器把整个工作台夹回 P1，导致已有 P2 交互模型也无法查看；深链 URL 仍保留被拒绝的目标页，刷新后再次错位。
- 根因：把“后续内容是否可生成”和“既有上游产物是否可查看”共用一个顺序门槛，并在恢复时同步 requested view 而非实际 active view。
- 永久规则：生成门槛只保护真正依赖该生成结果的下游页；已有 Flow / State / Interaction Model 永远按自身审核状态开放。任何路由夹取后，URL 必须 canonicalize 到实际 active view。
- 配置失败必须在队列前终止。正式服务器无内置 Key 且浏览器无 Key 时，明确显示“填写 API Key 后重试”；不创建 pending，不用 `generation_failed/system` 掩盖 configuration 原因。
- 页面浏览不是生成许可。进入 P7 只显示显式“生成完整预览”操作，点击前网络 POST 数必须为 0。
- 把隐式生成改成显式操作后，必须重新设计对应 idle state；左上角裸标题和按钮加大面积空白会让正确逻辑看起来像页面损坏。生成前状态应使用居中、可识别的正式状态卡。
- CSS 的高特异性恢复态可能击穿通用 `[hidden]`；恢复卡选择器必须配套 `[hidden] { display:none }`，并用截图而非仅 DOM state 验证无覆盖、无重叠。

# 2026-08-25 外部模型超时不能留下无期限 running

- 失败表现：页面长期停在“正在生成玩法目录”和 10%，刷新后仍不变化；数据库记录的 `updatedAt`、progress 和 message 数分钟完全不动。
- 根因：HTTP 客户端超时与重试不能替代业务任务总时限；工作线程阻塞时，job 没有 deadline watchdog，浏览器轮询只能重复读取同一条 running。
- 永久规则：队列写入时一次性生成 generation ID、开始时间和截止时间；后台独立 watchdog 到期后按 generation ID 原子转 failed/network。生成线程的 progress、success、failure 都必须按同一 ID 写入，迟到响应禁止覆盖恢复状态或下一次重试。
- 进度展示不得伪造线性增长。显示服务真实阶段、真实 progress、由 `startedAt` 计算的已等待时间，以及由 `deadlineAt` 计算的自动停止预期；到期后必须出现明确重试出口和原因。
- 验收不能只等正常模型返回。固定测试“调用中触发到期 → 保留骨架/最后有效版本 → 迟到成功结果被丢弃”，并以桌面截图验证阶段、百分比、时间、超时说明、无文字重叠和无横向溢出。

# 2026-08-25 截图导入中断不能遗留 queued/0%

- 失败表现：服务部署重启后，截图任务长期显示“等待处理 0%”，`updatedAt` 不再变化；job 的 frames 为空，但 frames/source_images/structures 文件可能已经完整落盘。
- 根因：job 在上传预处理前就创建为 queued；frames 只在整个 `persist_image_sequence` 返回后写入 job。重启恢复逻辑看到 image_sequence + empty frames 直接 `continue`，既不恢复也不失败。
- 永久规则：截图预处理必须提前写 expected-count manifest；恢复时只接受连续且相互匹配的 source/frame/structure 三联集。完整则重建 frames、scenes、componentTracks 和 `frames-complete` checkpoint；不完整则明确失败并引导重新选择原截图文件夹。
- 浏览器 Key 不得持久化。素材能恢复但服务端无可信 Key 时，状态必须是“素材已恢复，等待重新分析”，不能用空 Key 自动提交，也不能继续显示 queued。
- 验收矩阵固定包含：完整 manifest 恢复、legacy 完整三联集恢复、不完整文件明确失败、无服务端 Key 保留素材并等待显式重试、视频任务不受影响。
- 2026-08-25：章节级 Gameplay Model 生成可能合法地超过固定总时长。永久规则：生成页必须显示后端真实百分比和最近完成里程碑；超时只按“连续无进展时长”计算，每次章节或有效日志推进都刷新活动截止时间；终态必须可靠收敛为 completed/failed，禁止长期 running 造成假卡死。该规则覆盖所有旧项目、新项目和输入类型，不允许项目特判。

# 2026-08-25 未知操作必须转成策划决策，静态证据必须重新归位

- 失败表现：交互审核把“截图没有捕捉到操作”写成“静态帧无操作”；规则审核又把等级、收益、公式和画面展示塞进“玩法流程”，用户既无法确认真实操作，也无法审查真正的因果流程。
- 根因：系统把证据媒介当成玩家状态，并以字段非空代替语义归属；旧数据读取时没有执行同一套迁移，字符串字段还会被前端按数组展开为逐字列表。
- 永久规则：截图无法证明操作时，保持 unknown 并生成单选决策卡（点击、滑动、拖动、系统触发或自定义）；选择结果原子写回 transition、stage small loop 和 source page info。静态展示、当前数值、收益和公式不得进入 gameplay flow；旧项目读取时按通用语义重新归类且保留原文，人工确认内容不覆盖。所有列表入口必须先把 scalar/list 归一化，禁止字符串字符展开。
- 验收要求：一路狂飙、杂货铺、角色创建和全新项目使用同一生成与迁移路径；未知操作都有决策卡；静态/数值规则不出现在玩法流程；单字符串只生成一个列表项；编辑规则必须立即显示可编辑正文。

# 2026-08-26 不要用最终发布门槛拒绝可审核的 Grounded Draft

- 失败表现：用户点击“继续生成详细规则”，等待完整批次后又回到同一失败卡；重试多次仍重复。日志看似模型在工作，但每章都出现“已移除缺少依据的数值字段/计算公式”。
- 根因一：生成器把截图无法证明的数值和公式清理掉后，质量门禁仍要求 parameter schema/formula 达到最终发布标准，形成“生成→删除→缺失失败”的确定性矛盾。
- 根因二：13 章串行生成只在整批通过后写缓存。第 12 章上游 API 异常会让前 11 章全部丢失，下次从第 1 章重做，用户感知为无限循环。
- 根因三：per-chapter cache 构造时丢失 job identity，理论上相同证据/目录可跨项目复用响应，违反数据隔离。
- 永久修复：无证据参数/公式转成完整 Planner Decision；review-entry quality 允许该 pending 卡，但 delivery quality 继续严格。每章结构和证据清理通过后写安全检查点，网络失败保留、批次语义失败删除；缓存键保留 job/revision/evidence/contract。
- 诊断技巧：不要只看 UI 百分比。读取 generation logs，比较每章清理警告、lastProgressAt、终止章节和 failureKind；若持续出现清理警告，先检查质量门槛是否自相矛盾。若固定在后段失败，检查批量事务是否有安全检查点。
- 验收门槛：必须分别覆盖“缺证据值→决策卡→可进入 P4 但不可导出”“第 N+1 章断线→仅补该章”“批次语义失败→坏缓存清除”“两个项目相同截图仍不共用响应”。
