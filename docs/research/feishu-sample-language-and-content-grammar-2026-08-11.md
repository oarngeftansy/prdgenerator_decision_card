# 飞书样例的内容选择与语言组织语法

## 研究边界

结论只来自当前重新读取的《迷宫开发物语功能文档-1219 副本》revision 61 与《【Gve16】执行文档261008 Copy》revision 47。旧研究中“矿坑、组队、迷雾、事件池”等无法在当前迷宫文档中定位的内容不参与归纳。

## 作者先决定写什么

作者并未给每个机制套同一目录，而是先判断该机制要帮助制作人员回答什么问题：

- 总览先回答玩家做什么、何时成功、何时失败。迷宫样例在同一组连续句中完成目标与胜负边界，没有先解释所有对象属性。
- 放置类规则回答资格、冲突与失败回退。背包规则将“形状匹配”“已有占用”“不匹配退回”放在相邻列表中。
- 随机类规则回答进池资格、栏位关系、抽取顺序、重复/空结果、暂存、确认、刷新成本和重置。GVE16 因规则确实复杂才逐步下钻。
- 数值类规则把配置字段或公式与行为说明分载体。正文解释用途和关系，表格/命名配置承担数值，不在正文重复整张表。
- 状态型规则在行为之后补保留或重置边界。局内资金将正常结束清除与中断恢复保留并列，避免笼统写“关卡结束重置”。

## 篇章组织

默认顺序是“目标或触发 → 资格/条件 → 系统处理 → 玩家选择或系统反馈 → 失败/重复/重置”。这不是固定标题，而是因果阅读顺序。只有存在真正的多步算法时才编号；短规则用一个段落收束，多个短兄弟机制可合并进同一业务部分。

当表格、截图或画板已经承担信息时，正文只解释其策划含义：配置表承担字段和值，截图承担可见布局，画板承担页面与状态关系。正文不复述每个单元格、视觉位置或连线。

## 句子组织

- 条件前置：“相同类型和局内等级的魔物可以……”；读者先知道规则何时适用。
- 动作紧跟结果：“提升局内等级后……外观会变化并且会提升战斗数值”；反馈与操作不分散。
- 生命周期放句末：“随着关卡结束而重置”；让范围约束贴近受约束状态。
- 对互斥边界使用对照句：正常结束清除，中断后继续则保留。
- 确定规则使用陈述句；证据不足的内容不靠“可能、大概”混入正文，而转为策划决策。

## 标题与密度选择

标题服务于业务导航，不服务于填表。一个标题下只有一两句时，优先与相邻同层机制合并；一个机制需要多组独立规则、表格或算法时才保留独立标题。样例可迁移的是选择条件，不是平均标题数或固定篇幅。

## 不同机制为什么使用不同结构

| 机制形态 | 作者优先回答 | 常见组织方式 | 不应强制出现 |
|---|---|---|---|
| 简单移动或状态 | 发生什么、玩家能控制什么、失败边界 | 一个紧凑段落 | 配置、公式、验收小节 |
| 放置或拖拽 | 放置资格、占用冲突、失败回退 | 条件句加短列表，必要时配图 | 独立生命周期小节 |
| 内容容器 | 有哪些槽位/类型、初始状态、容量与填满后行为 | 完整内容清单加边界 | 把多个对象概括为“存在多种内容” |
| 随机机制 | 进池、顺序、放回、重复/空结果、暂存与确认 | 资格清单与真实算法步骤 | 没有证据的概率或权重公式 |
| 表现/演出 | 触发条件、画面顺序、结束状态 | 有序步骤与截图 | 后端公式和持久化推断 |
| 配置型成长 | 行为含义、字段归属、不可逆或重置范围 | 短正文加一张配置表 | 正文重复每个字段值 |
| 计算/统计 | 变量、表达式、顺序、取整、显示与算例 | 公式后紧跟展示规则 | 变量未知时编造算例 |
| 前后端同步 | 谁预计算、谁演出、何时校验、何时补同步 | 按时间节点写职责 | 仅写最终玩家可见结果 |
| 关卡外入口 | 解锁资格、资源扣除时点、失败返还、重复限制 | 条件—扣除—结果—边界 | 与关卡内状态混写 |

## 画板、截图与正文的职责

GVE16 把 UX、策划草图、竞品参考分成三个画板。`doxcnLz8pBejxMzQCs0uXcnfWYd` 明确视觉样式以 UX 为准；策划草图与竞品参考分别使用独立画板块。因此迁移规则是：策划画板表达页面节点、玩家操作和跳转；竞品画板解释参考关系；最终视觉样式不能由策划草图冒充。正文负责可实现规则，不重复画板的空间连线。

局部截图只承担“可见状态的证据”。例如武器栏截图可证明图标、累计词条数和冷却表现的布局，但“默认栏固定”“自选栏填满后不能获得新类型”仍由相邻规则文本提供，不能从截图推导。

## 参数命名的载体逻辑

GVE16 的载具等级段落并未先建立通用字段字典。作者先用行为正文说明初始等级、升级消耗和属性变化，再在同一机制下逐行写“等级：配置在 GVE16 载具表 level 字段”“攻击力：GVE16 载具表 atk 字段”等就近命名映射，最后补不可逆与活动结束重置。由此得到可迁移规则：

- 行为正文：说明机制如何发生及产生什么结果。
- 就近命名映射：按 `业务名 → 配置表/字段名` 逐行展示，让实现名称保留业务语境。
- 配置表：集中承载值、单位、范围、默认值和来源，不让正文重复单元格。
- 生命周期：紧跟机制结尾，说明不可逆、保存、清除和重置范围，不混进字段表。

正式配置表名和字段名必须有参考文档、配置表或策划决定支持。当前项目只有截图证据时，只能写 `建议程序字段名（待程序/配置表确认）`，不得仿造样例中的正式表名。不得用集中字段字典总表替代上述四类载体；集中表只可作为确有跨机制检索价值的附加索引，不能成为默认正文结构。

当规则涉及多个执行方时，作者会直接写职责与同步时机。迷宫掉落章节明确：后端在波次开始预计算，前端在击败勇者时播放演出，局内升级与全部波次结束时再同步验证；三选一因前后结果相互影响，不能提前计算。这类信息不是生命周期补充，而是实现契约，应单独列为适用维度。

## 省略逻辑

内容被省略有三种不同原因：没有可靠证据；对实现和验收没有新增价值；已经由表格、截图或画板完整承载。审计必须记录是哪一种，不能把“没写”一律当缺陷，也不能把“表格已有”误判成正文不足。

## 非样例迁移盲测

使用当前项目的“载具移动 + 生命值”短机制作为非样例材料。第一遍只保留可见事实：载具沿路线自动前进、玩家可横向控制、受伤扣减生命、生命归零后本局失败、无效攻击不扣血。第二遍按内容语法组织为一个“核心战斗”业务部分，下设两个紧凑段落；未添加配置表、公式、刷新、概率或跨局生命周期。结果迁移了条件—动作—结果与短机制合并规则，但没有复制魔物、词条、资金、重 Roll、样例数值或样例标题。

为避免只验证一种短机制，盲测扩展为三种不同形态，完整结构保存在 `data/calibration/gve16/transfer-blind-test.json`：

1. **稀疏状态机制**：载具移动与生命值合并为一个业务部分，使用两个紧凑段落。语言主语分别选择“载具”和“玩家”，边界贴在受影响状态之后；没有公式与配置来源，因此不生成对应模块。
2. **交互反馈机制**：升级选择的页面关系进入策划草图，正文使用“页面展示 → 玩家点击 → 效果生效 → 返回战斗”的因果链。刷新入口只能证明可见次数，正文明确停止在证据边界，不推导算法、概率或恢复规则。
3. **复杂执行算法**：奖励候选的结果依赖筛选、去重、排序和填位顺序，因此使用编号步骤；优先级数值由来源表承担，正文只解释字段作用；候选不足作为算法末尾边界，不另建空泛小节。

三种输出分别使用合并正文、策划草图加因果正文、有序算法加来源表，章节数量也不同。自动测试同时禁止出现样例专属的对象名、配置名、数值和固定标题。这证明迁移目标是作者的推理与表达选择，而非复制样例外形。
