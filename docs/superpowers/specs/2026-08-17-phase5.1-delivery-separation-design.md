# Phase 5.1 Logic / Presentation Delivery Separation Design

## Objective

Phase 5.1 separates delivery carriers without changing content authority. The Execution Document carries approved Logic/Data execution rules. The Visual / Interaction Board carries approved Presentation Rules and their evidence-backed visual context.

This phase does not modify the Entity Graph, Rule, Gap, parameter data, P7 export, the current UI, or the eight-step product flow. It produces independent reference and audit artifacts only.

## Locked public interfaces

```python
build_visual_blocks(
    presentation_rules,
    logic_rules,
    entity_graph,
    evidence_index,
) -> list[VisualBlock]

build_logic_only_delivery(
    chapters,
    mechanism_blocks,
    visual_blocks,
    style_profile,
) -> ExecutionDelivery
```

Both interfaces are deterministic, do not call an LLM, and treat their inputs as immutable.

## Execution Document contract

The Logic-only Execution Document may read only Rules whose `ruleType` is one of:

- `logic`
- `flow`
- `numeric`
- `config`
- `interaction`

Presentation Rules are not rendered as ordinary paragraphs, bullets, headings, configuration rows, or open decisions.

When a Logic Rule has a deterministic association to a VisualBlock, its rendered mechanism paragraph may append one short reference:

> 相关表现见策划草图 VIS-XXX。

The reference is forbidden when the VisualBlock has no deterministic `relatedLogicRuleIds`. It never repeats `presentationDescription` in the Execution Document.

## VisualBlock contract

Each approved Presentation Rule creates exactly one stable VisualBlock:

```text
visualBlockId
relatedEntityIds[]
relatedRuleIds[]
relatedLogicRuleIds[]
evidenceIds[]
screen
state
visualElement
triggerReference
presentationDescription
interactionAnchor
sourceScreenshotIds[]
```

### Stable identity

`visualBlockId` is derived only from the Presentation Rule ID and remains stable across regenerations while that Rule ID is unchanged. One Presentation Rule maps to one VisualBlock; Presentation Rule → VisualBlock coverage must be 100%.

### Entity association

`relatedEntityIds[]` is copied from the Phase 5 audited `presentationRuleReferences`. Phase 5.1 does not resolve aliases, infer new entities, change EntityType, change relationships, or alter `primaryDefinitionChapter`.

Every VisualBlock must resolve at least one existing Entity ID. A missing or unknown audited Entity ID is a hard validation error, not an invitation to infer one.

### Logic association

`relatedLogicRuleIds[]` is populated only by the following deterministic precedence:

1. Use an explicit Logic Rule ID recorded in the Presentation Rule, when it references an existing approved non-presentation Rule.
2. Otherwise require all three conditions simultaneously:
   - the Presentation Rule and Logic Rule share at least one audited Entity ID;
   - their mechanism semantics are compatible under an explicit compatibility table;
   - their evidence chains intersect through the evidence index.
3. Include every Logic Rule that independently satisfies all three conditions. If a candidate cannot pass them deterministically, omit that candidate; if none pass, keep `relatedLogicRuleIds[]` empty.

Shared Entity alone, shared chapter alone, or keyword similarity alone is insufficient. Logic association coverage is not a target metric.

### Evidence and screenshots

`evidenceIds[]` copies the Presentation Rule evidence IDs.

`sourceScreenshotIds[]` may contain only IDs that the supplied `evidence_index` explicitly identifies as screenshots. Evidence IDs, Fact IDs, Rule IDs, frame descriptions, timestamps, and filenames inferred from prose cannot be promoted to screenshot IDs. If no real screenshot index is available, the array remains empty.

### Visual fields

`screen`, `state`, `visualElement`, `triggerReference`, and `interactionAnchor` are populated only from structured fields or a deterministic, evidence-preserving projection declared in the evidence index. Missing values remain empty. `presentationDescription` is the unchanged approved Presentation Rule behavior.

## Mechanism semantic compatibility

Compatibility is content-neutral and declared by schema semantics, not free text. Initial Phase 5.1 compatibility supports only pairs proven by existing structured slots and chapter ownership, such as:

- movement presentation ↔ movement logic in the same Entity mechanism domain;
- attack presentation ↔ attack/damage logic in the same Entity mechanism domain;
- random presentation ↔ randomization logic in the same candidate/container domain;
- settlement presentation ↔ settlement logic in the same process/report domain.

The table cannot create a missing Logic Rule. If shared Entity, compatible mechanism semantic, and evidence-chain intersection do not all hold, no association is emitted.

## Data flow

```text
Approved Rules
├─ non-presentation → existing MechanismBlocks → Logic-only delivery filter
└─ presentation → Phase 5 audited Entity references → VisualBlocks

VisualBlock.relatedLogicRuleIds
└─ explicit ID OR (shared Entity + compatible semantic + evidence-chain intersection)

Logic-only delivery
└─ optional stable VIS reference only for deterministically linked blocks
```

Presentation remains downstream of Logic. It cannot create or modify a Logic Rule, close a Gap, create an Entity, change an Entity relationship, or influence primary definition ownership.

## Six-chapter reference audit

The independent Phase 5.1 artifact covers:

- 载具移动
- 武器攻击
- 三选一
- 怪物攻击
- 关卡
- 结算

For each target it displays:

```text
Phase 4.3 text
→ Phase 5.1 Logic-only text
→ associated VisualBlocks
```

This artifact is not written back to P7 and does not replace P3 or P5:

- P3 remains interaction-deliverable review.
- P5 remains diagram review.

## Validation metrics

Phase 5.1 reports:

- Presentation Rule count
- VisualBlock count
- Presentation → VisualBlock coverage; target 100%
- VisualBlock → Entity resolution; target 100%
- VisualBlock → Logic deterministic association count
- VisualBlocks with empty `relatedLogicRuleIds`
- Presentation backflow into Logic; must be 0
- Presentation Rules in Execution Document; must be 0
- Logic / Presentation duplicate descriptions; target 0
- Execution Document → VisualBlock stable-reference resolution; target 100%
- unsupported semantic additions; must be 0

## Failure handling

- Unknown Phase 5 Entity reference: fail VisualBlock validation.
- Duplicate VisualBlock ID: fail generation.
- Non-screenshot value in `sourceScreenshotIds`: fail validation.
- Presentation Rule found in Logic-only delivery: fail generation.
- VIS reference without a deterministic Logic association or without a target block: fail generation.
- Ambiguous Logic association candidate: omit that candidate and record the block in the audit; other independently proven candidates remain valid.

## Non-goals

- No ParameterResolver.
- No Entity Graph changes.
- No Rule or Gap changes.
- No Presentation-to-Logic inference.
- No screenshot generation or UI redesign.
- No P3/P5/P7 mutation.
- No complete new production document.
