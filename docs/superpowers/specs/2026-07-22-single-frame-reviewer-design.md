# 单帧关键帧复核器设计规格

## 1. 目标

把当前同时铺开多张关键帧的复核区改成一次只查看一张关键帧的复核器。用户通过左右箭头按视频时间顺序检查全部关键帧，并在截图旁阅读或修正通俗、可直接进入策划案的文字说明。

玩法策划和交互策划共享同一套浏览交互，但显示不同的说明字段。用户界面和最终策划案遵循 GVE16 示例的自然语言风格，不直接暴露研发数据模型术语。

## 2. 成功标准

- 一次只显示一张关键帧及其完整说明。
- 全部关键帧严格按时间戳从早到晚排列，不漏帧、不重复、不跳号。
- 左右按钮、键盘方向键、场景时间线和待审核队列始终定位到同一张关键帧。
- 玩法模式显示玩法、规则、条件、数值和反馈；交互模式显示界面内容、用户操作、显示条件、提示和去向。
- 用户修改说明后切换关键帧，内容不会丢失。
- 文字表达与 GVE16 示例一致，使用“点击后发生什么”“什么情况下显示”“成功/失败条件”等通俗说法。

## 3. 页面结构

### 3.1 桌面端

采用已确认的 A 方案：左图右文。

- 顶部导航栏：上一帧按钮、场景名称、帧 ID、视频时间、当前位置/总数、下一帧按钮。
- 左侧图片区：当前关键帧大图；提供“跳到原视频此处”。
- 右侧说明区：当前模式对应的字段、证据等级、置信度、待确认项和确认按钮。
- 图片区约占可用宽度的 58%，说明区约占 42%。具体比例可根据现有容器宽度微调，但图片始终是主要视觉内容。

### 3.2 移动端

自动改为上图下文：导航栏、截图、说明区依次排列。页面不得产生横向滚动，上一帧和下一帧按钮保持至少 44×44 像素的可点击区域。

## 4. 浏览与编辑交互

- 初次进入时显示时间最早的关键帧；从场景或待审核项进入时直接显示目标帧。
- 点击左右箭头按时间顺序切换全部关键帧。
- 支持键盘左、右方向键。光标位于输入框、文本框或下拉框时，不接管方向键。
- 第一帧禁用上一帧按钮；最后一帧禁用下一帧按钮，并给出可读的禁用说明。
- 当前位置使用“27 / 140”形式显示。
- 修改说明后沿用现有防抖保存。切换帧时立即把当前修改放入保存队列，再更新画面。
- 点击“确认此帧”后保留在当前帧，并更新确认数量。用户可以继续修改并再次保存。
- 点击场景时间线、证据点或待审核项时，复核器切换到对应帧，并同步原视频播放位置。
- 切换帧后，把键盘焦点放到复核器标题区域并播报新帧编号，避免屏幕阅读器用户失去位置。

## 5. 玩法模式说明格式

右侧按以下顺序显示：

1. **这一段在玩什么**：当前关卡环节或游戏状态。
2. **玩家现在要完成什么**：本阶段目标。
3. **玩家做了什么**：输入方式、操作对象和目标对象。
4. **游戏接着发生了什么**：游戏对操作的直接响应及后续变化。
5. **什么时候算成功 / 失败**：视频明确展示的判定条件；未展示时写“视频未展示，待确认”。
6. **有哪些玩法规则**：触发条件、限制、循环或特殊情况。
7. **数值和进度发生了什么变化**：生命、时间、奖励、分数、资源或关卡进度。
8. **画面和声音给了什么反馈**：动画、特效、音效、震动、飘字或提示。
9. **还需要确认什么**：画面未展示、证据不足或存在多种解释的内容。

不要求每张关键帧都填满所有内容。没有证据的字段显示“视频未展示，待确认”，不得根据常见游戏做法补成确定规则。

## 6. 交互模式说明格式

右侧按以下顺序显示：

1. **当前是什么界面**：页面、弹窗、浮层或局部区域的名称与用途。
2. **这个界面需要显示什么内容**：用户可见的信息、按钮、输入项和提示。
3. **用户进行了什么操作**：点击、输入、拖动、滑动、滚动、等待等实际动作。
4. **进行操作需要满足什么条件**：解锁、填写完整、已有选择、权限或其他前提。
5. **点击或操作后发生什么**：界面反馈、内容变化、数据变化或请求结果。
6. **不同情况下分别怎么显示**：平时、处理中、完成、失败、不可操作等情况，用自然语言逐项说明。
7. **页面上出现什么提示文字**：按钮文字、Toast、错误提示、说明文案等可见内容。
8. **操作完成后进入哪里**：停留当前页面、关闭弹窗、打开新页面或返回上一层。
9. **视频没有展示什么**：弱网、失败、重复点击、权限不足、空内容等未展示情况。

## 7. 用户语言与内部数据的边界

内部仍可保留稳定的数据字段，方便模型、质量审计和流程图复用；这些字段不得直接成为界面标签或策划案标题。

| 内部含义 | 用户看到的说法 |
|---|---|
| 默认显示状态 | 平时怎么显示 |
| 处理中状态 | 操作后等待时怎么显示 |
| 成功状态 | 成功后发生什么 |
| 失败状态 | 失败时怎么提示 |
| 操作前状态 | 操作前是什么情况 |
| 操作后状态 | 操作后变成什么情况 |
| 触发方式 | 用户做了什么 / 什么情况下触发 |
| 组件层级 | 这个内容位于界面的什么位置 |
| 校验错误 | 什么情况下不能继续，以及如何提示 |

最终策划案优先使用 GVE16 示例中的表达结构：界面内容、显示条件、解锁条件、点击后、不同情况、胜利条件、失败条件、提示文字和结果去向。

## 8. 数据兼容

- 复用现有 `state.frames` 和后端关键帧数据，不改变已保存任务的基本结构。
- 新增一个当前帧索引，由排序后的关键帧数组驱动。
- 旧任务缺少模式专属字段时，从现有操作前情况、用户操作、系统响应、操作后情况和未知项生成可读的兼容显示。
- 模式来自任务元数据。打开历史任务时按任务原有模式展示，不因当前下拉框值而误用另一套格式。
- 后端和最终文档继续保留稳定证据 ID、帧 ID 和时间戳，界面只改变显示名称与组织方式。

## 9. 状态与错误处理

- 没有关键帧：显示上传和分析引导，不渲染空导航器。
- 图片加载失败：保留帧编号、时间戳和文字说明，提供重新加载图片按钮。
- 保存失败：保留本地修改并标记“尚未保存到任务”，允许继续浏览；用户重试成功前不得把任务标记为审核完成。
- 目标帧不存在：定位到时间上最近的一帧并提示原证据已不可用。
- 后端任务仍在处理中：复核器显示已经产生的帧，并说明总数仍可能增加；任务完成后保持当前帧不跳动。
- 低置信度或待确认：用文字和图标同时提示，不只依赖颜色。

## 10. 范围

本次包含：单帧复核器、顺序导航、键盘操作、玩法/交互说明格式、通俗化标签、现有跳转入口联动、移动端适配和保存反馈。

本次不包含：重新设计整站导航、修改视频抽帧算法、自动创建飞书/Figma 文件、合并两个示例关卡为一个任务或改变 GVE16 文档的章节范围。

## 11. 验收与测试

- 单元测试：排序、首尾按钮、目标帧定位、模式字段映射、技术术语到通俗文字的转换。
- 交互测试：按钮切换、键盘切换、输入时方向键不切帧、编辑保存、保存失败时保留本地修改并阻止审核完成。
- 集成测试：历史任务、场景时间线、证据点和待审核队列均能定位正确帧。
- 模式测试：相同证据分别在玩法和交互模式下显示对应说明结构。
- 内容测试：界面不得出现 `default`、`loading`、`success`、`error`、`beforeState`、`afterState`、`component tree` 等内部标签。
- 响应式测试：桌面左图右文；移动端上图下文；无横向溢出。
- 可访问性测试：箭头具备文字标签、清晰焦点、禁用状态和键盘导航；低置信度提示不只依赖颜色。
- 回归测试：使用两个示例视频任务浏览全部关键帧，确认顺序、编辑和模式语言符合 GVE16 示例。
