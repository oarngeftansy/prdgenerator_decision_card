# 飞书原生策划案发布设计

## 1. 目标

在本地网站完成视频分析、关键帧复核和策划案生成后，由策划主动点击“发布到飞书”，将最终结果写入用户自己的飞书空间。策划案以飞书原生文档交付；UE 流转图等适合图示的内容以文档内嵌飞书画板交付。

默认归档目录为用户“我的空间”下的固定文件夹“视频策划案生成中心”。发布失败不得破坏本地任务、策划案或已成功写入的飞书内容。

## 2. 已确认的产品行为

- 不在分析完成时自动发布；只有用户点击“发布到飞书”才产生外部写入。
- 首次发布时查找固定文件夹“视频策划案生成中心”，不存在才创建，后续持续复用。
- 每个本地任务对应一份飞书策划案文档。
- 文档命名为“项目名｜玩法策划案｜YYYY-MM-DD”或“项目名｜交互策划案｜YYYY-MM-DD”。
- 首次发布创建文档；再次发布默认更新同一份文档。
- 用户可以选择“另存为新版本”，创建带版本后缀的新文档。
- 发布成功后，网站显示“打开飞书文档”，并保留文档与画板的外部标识。

## 3. 技术方案

采用本地后端调用 `lark-cli` 的方式，以当前已登录的飞书用户身份执行写入。网站前端不接触飞书 access token，不在浏览器存储飞书密钥，也不引入独立云端服务。

新增三个边界清晰的组件：

1. `FeishuPublisher`：负责检查用户登录状态、解析 CLI JSON 信封、创建或定位固定文件夹、执行文档发布与状态恢复。
2. `FeishuDocumentRenderer`：把已经验证的 GVE16 中间策划模型渲染为飞书 XML，不从 Markdown 反向猜测结构。
3. `FeishuFlowRenderer`：把 UE 节点和连线渲染为 Mermaid；后续确有复杂视觉布局时，才升级为 SVG 或白板 DSL。

这三个组件只依赖稳定的策划模型和一个可替换的 CLI 执行接口，便于单元测试时使用假的执行器，不需要真实写入飞书。

## 4. 发布数据流

1. 用户完成关键帧复核并生成策划案。
2. 用户点击“发布到飞书”。
3. 前端向本地后端提交任务 ID、发布方式（更新或另存新版本）和一次性幂等请求 ID。
4. 后端校验任务已完成、策划模型存在且质量审计满足发布条件。
5. 后端检查 `lark-cli` 和用户登录状态。
6. 后端查找固定文件夹；仅在不存在时创建。
7. 渲染玩法或交互对应的飞书 XML，并把 UE 流程渲染为内嵌 Mermaid 画板。
8. 创建或更新文档；关键帧图片按文档章节插入并附时间点说明。
9. 回读文档，验证标题、章节、关键帧和画板均存在且画板不是空白占位。
10. 将公开链接、文档 token、画板 token、发布状态、飞书 revision、发布时间写回本地任务。
11. 前端显示成功结果与“打开飞书文档”。

## 5. 飞书文档结构

文档遵循 GVE16 样例的自然语言与章节颗粒度，不暴露内部字段名或模型术语。正文使用连续段落表达分析，真正的行列数据才使用表格，检查项才使用待办，避免把全文组件化。

共享内容包括项目背景、视频范围、结论摘要、证据说明、待确认项与版本信息。玩法策划案重点呈现玩家目标、核心机制、操作规则、状态变化、数值与资源、胜负条件、反馈和关卡流程；交互策划案重点呈现用户任务、页面/弹窗/组件、显示与解锁条件、输入事件、系统响应、前后状态、异常路径和结果去向。

关键结论附近插入对应关键帧图片，并显示可读时间点和证据等级。文档标题只出现一次，避免文档标题与正文首个标题重复。

## 6. UE 流转画板

UE 流程是图示明显优于文字的内容，因此作为文档内嵌画板生成。第一版统一使用 Mermaid，以保证节点、连线、分支和文本均可编辑、可稳定重建。

- 玩法画板节点强调进入条件、玩家操作、玩法状态、规则判断、成功/失败与反馈。
- 交互画板节点强调页面或组件状态、用户输入、系统响应、分支条件、异常状态与结果去向。
- 节点文案使用策划可读的中文，不直接显示 `default-loading` 等内部命名。
- 每次写入使用稳定幂等标识；同一次重试不得重复生成节点或画板。
- 创建后必须回读或导出预览验证。只有包含有效节点和连线才标记为成功。

若某个复杂图无法由 Mermaid 清晰表达，后续可在不改变发布接口的情况下把该图升级为 SVG/白板 DSL；第一版不引入这项复杂度。

## 7. 更新、版本与人工编辑保护

本地任务保存最后一次成功发布的文档 token、revision 和内容指纹。重复发布时先读取当前飞书 revision：

- revision 与上次发布一致：允许更新同一文档。
- revision 已变化：视为用户可能在飞书内人工编辑，禁止静默覆盖；前端提示“飞书文档已有修改”，建议另存为新版本。
- 用户选择另存新版本：创建“原文档名｜V2、V3……”并建立新的发布记录。

图片上传、正文创建和画板写入分别记录状态，使部分成功可恢复。重试时复用已经成功创建的资源，不重复创建文件夹、文档或画板。

## 8. 状态与错误处理

发布状态包括：`not_published`、`checking_auth`、`creating_folder`、`creating_document`、`uploading_evidence`、`creating_whiteboard`、`verifying`、`published`、`partial`、`failed`、`conflict`。

- 未登录或授权过期：提示用户完成飞书用户授权，不丢失本地内容。
- 权限不足：只显示缺失的权限与授权动作，不显示 token 或底层密钥。
- 文件夹创建失败：停止后续写入，可安全重试。
- 文档成功、图片或画板失败：保留文档并标记为部分成功，允许从失败步骤继续。
- 网络中断或超时：使用原幂等请求 ID 重试。
- 文档被人工修改：进入冲突状态，不自动覆盖。

## 9. 网站交互

输出区新增主按钮“发布到飞书”。点击后按钮原位显示当前阶段，不跳转页面。成功后按钮区域显示“已发布到飞书”“打开飞书文档”“更新飞书文档”和“另存为新版本”。

首次使用且未登录时，网站显示清晰的飞书授权引导；授权完成后用户再次点击发布。失败信息使用策划可理解的语言，例如“飞书登录已过期”“画板暂未创建成功”，不直接展示 CLI 堆栈或内部错误码。

## 10. 本地持久化与安全

任务数据只保存公开 URL、资源 token、revision、内容指纹、状态和时间，不保存飞书 access token、refresh token、App Secret 或视觉模型 API Key。CLI 登录态由 `lark-cli` 自身管理。

后端只能执行白名单中的飞书命令与参数，不接受前端传入任意命令、文件路径或 shell 文本。所有临时 XML、Mermaid 和图片清单必须位于任务的受控临时目录；日志和 API 响应不得回显凭证。

## 11. 验收标准

- 第一次发布只创建一个固定文件夹和一份对应模式的文档。
- 重复同一请求不会产生重复文档或画板。
- 文档正文使用飞书原生结构，玩法与交互章节不同且符合 GVE16 表达。
- 关键帧图片与时间点能在相应结论附近查看。
- UE 流程以非空内嵌画板出现，节点和连线可读。
- 飞书人工编辑发生后，网站不会静默覆盖。
- 文档、图片或画板部分失败后可以从断点重试。
- 成功后本地任务包含可打开的飞书链接，但不包含任何凭证。
- CLI 缺失、未登录、权限不足、网络失败和冲突状态均有可理解提示。

## 12. 非目标

- 第一版不部署独立云端飞书应用服务。
- 第一版不支持任意自定义飞书文件夹层级。
- 第一版不自动发布未经用户确认的策划案。
- 第一版不把所有图示都转成画板，只处理 UE 流转等图示价值明确的内容。
- 第一版不覆盖或修改用户提供的 GVE16 样例原文档与原画板。
