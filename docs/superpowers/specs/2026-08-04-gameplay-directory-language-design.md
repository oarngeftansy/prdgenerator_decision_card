# 玩法目录语言分层设计

## 目标

玩法目录供主策快速确认 AI 是否理解了实际玩法结构。目录顶部概述和各章节摘要必须描述玩法目标、循环、机制边界与规则范围，不得逐帧复述页面布局、控件、弹窗、特效或截图数字。

## 信息分层

### 顶部玩法理解

最多四句话，依次说明：

1. 玩家在局内持续完成的主要行为与目标。
2. 推动循环变化的成长、资源或阶段机制。
3. 核心循环的因果顺序。
4. 当前素材仍无法确认的关键玩法规则。

不得出现屏幕方位、按钮位置、界面名称、视觉样式或单次截图数字。

### 目录章节摘要

每项用一至两句话说明该章节将定义的玩法规则，包括适用范围、触发条件、玩家选择、状态变化和结果。摘要不使用“本章将说明”作为机械前缀，直接陈述机制范围。

摘要只陈述素材已经支持的玩法结论，不出现“需要在本节定义”“请策划确认”“后续需要补充”等任务指令。无法确认的触发条件、概率、永久性、互斥关系和边界规则移入独立的待确认事项。

示例：

- 原文：玩家升级或特定触发时进入“选择武器”界面，从三个随机词条中选择一个。
- 改写：局内成长触发后，系统从候选池提供三项强化，玩家选择一项立即改变本局能力。

- 原文：存在一种名为“终极词条”的高稀有度物品，获取后会提示“进入词条库”。
- 改写：终极词条是高稀有度成长内容，获取后会加入词条库，并参与后续玩法循环。
- 待确认：终极词条的出现条件、是否永久入库、后续抽取概率及互斥规则。

### 章节内证据

界面位置、弹窗、按钮、金色边框、爆炸特效、伤害飘字及截图中的具体数值保留为交互证据或参数证据，不进入目录摘要。证据不得删除，只改变展示层级。

### 项目专有名词

工作台和最终文档优先使用跨项目都能理解的策划通用名称。素材中的专有名词首次出现时使用“通用名称（素材中称‘原名’）”，后续统一使用通用名称；只有逐字引用界面文案时保留原名。

例如将“词条”表达为“强化效果（素材中称‘词条’）”，将“终极词条”表达为“终极强化”。不得默认策划已经理解原游戏的内部命名。

## 生成逻辑

目录生成优先使用章节的玩法类型、机制描述和规则字段组织摘要，不直接拼接前若干条截图声明。若只有截图声明，先按以下顺序抽象：玩家目标 → 触发与选择 → 状态变化 → 玩法结果。

过滤仅针对目录展示文本，不修改底层声明、证据截图、参数或可信度。

## 当前任务迁移

现有任务已经生成的九个章节不重新调用视觉模型。系统根据已保存的章节机制和声明重建目录顶部概述及每项摘要，保留目录顺序、章节内容和十五张证据图。

## 验收标准

- 顶部概述不超过四句话。
- 目录摘要不出现屏幕方位、按钮、弹窗、颜色、边框、特效等交互描述。
- 目录摘要不直接堆叠截图数字。
- 项目专有名词首次出现时有通用名称解释，后续不重复堆叠括注。
- 每项摘要能明确说出该章节负责定义的玩法机制。
- 交互和视觉信息仍能在章节证据中查到。
- 当前任务刷新后直接显示迁移后的摘要，无需重新生成玩法章节。

## 测试

- 用包含方位、控件、视觉反馈和数字的声明验证目录只输出玩法抽象。
- 用“随机三选一”和“终极词条入库”验证选择、稀有度、入库和概率规则被保留。
- 验证底层声明及证据数量在目录重建前后完全一致。
- 验证刷新与交互模型同步不会覆盖迁移后的目录文本。

## 交互策划草图对齐

网页预览与飞书原生白板必须使用同一份策划草图结构，避免审核版本与最终交付版本不一致。

结构顺序固定为：完整主流程 → 功能阶段 → 阶段内小流程。每个功能阶段使用真实截图作为主要证据，并按用户最新提供的飞书策划白板组织主线、分支、模块边界和局部说明。

前进、进入和打开使用实线；返回、关闭和回环使用虚线。连接线优先保持水平或垂直。异常、跨状态约束和待确认结论统一使用淡黄色注记，不挤入正常操作步骤。

网页预览和飞书白板共同消费同一份中间结构：阶段、代表截图、规则文本、前进关系、返回关系和黄色注记。任何一端不得自行重新推导流程层级。

红色数字标记及其配套编号规则属于后续 UE 流转图能力。本版本保留已有编译能力和扩展字段，但默认策划白板不启用编号标记，也不把编号作为验收条件。

### 草图验收

- 网页预览与飞书原生白板具有相同的阶段顺序、截图、规则文字和连线方向。
- 主流程可从左到右连续阅读，阶段内细节向下展开。
- 实线与虚线语义正确，不能出现无方向或交叉遮挡主要内容的连线。
- 与用户最新提供的飞书策划白板相比，主线、阶段分组、局部流程和分支结构一致后才生成完整白板。
