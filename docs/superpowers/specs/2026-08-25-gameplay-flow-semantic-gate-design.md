# Gameplay Flow 语义门禁设计

## 目标

目录骨架只能证明“有哪些机制”，不能冒充详细玩法规则。所有已有项目、新建项目和输入类型必须在详细 Gameplay Model 完成并通过语义质量门禁后，才能进入 P4–P7。

## 全局不变量

- 所有项目执行同一套标准、边界、规则分类、推理约束、质量门禁和修复策略；禁止按项目名、历史案例或输入来源设置专用捷径。
- 任务数据、生成上下文、缓存、失败状态与最后有效版本必须按 `jobId + evidence revision + approved model revision` 隔离，不能跨项目读取、复用或回填。
- System Lesson 只能保存可迁移的判断逻辑，不得保存任何项目的规则答案、标题、数值或专用文案。
- 旧项目迁移、新项目首次生成、重试、刷新和失败恢复必须经过同一组验证器。

## 数据责任

1. `ruleType=flow/interaction/logic` 的规则只有在表达运行时行为时，才可参与玩法流程候选。
2. `presentation` 进入规则理解或表现规则；`numeric` 进入参数/数值规则；`config` 进入配置规则，不得进入 `normalFlow`。
3. 已批准规则只重新分配展示责任，不修改其原始文本、数值、触发条件或权威状态。

## FlowChain 门禁

详细章节的玩法流程按五个职责检查：触发、玩家操作、系统反馈、状态变化、出口。

- 不要求每章机械写满五句；纯表现、纯参数章节可以没有玩法流程。
- 一旦章节声明存在玩法流程，至少必须形成“触发/操作 → 系统反馈或状态变化”的因果链，并提供出口或明确该机制持续运行。
- 静态画面、当前数值、UI 显示和规则边界单独出现时，不算流程节点。
- 不合格流程进入质量错误，不能确认章节，也不能开放图解、参数和文档导出。

## 质量状态

模型分别保存：

- `structureQuality`：目录系统、子系统、机制的层级与证据质量。
- `detailQuality`：详细规则密度、FlowChain、参数、边界和验收质量。

`generationQuality` 仅作为兼容读取别名，不再作为阶段真相源。网页必须按当前阶段显示对应质量，不能把结构分显示为详细规则分。

## 网页行为

- `pending/detail_generation_pending` 或 `detailQuality.passed=false`：停留 P1，展示生成或修复进度。
- P4 只渲染经过责任分流的流程、关键规则、参数与表现内容。
- 纯表现/纯参数章节不显示空的“玩法流程”，也不因此伪造流程。
- 质量失败必须显示可理解的原因，并允许保留最后有效详细版本或重新生成。

## 回归矩阵

建立四类固定夹具：

1. 《一路狂飙》：包含真实触发、操作、反馈、状态与出口的流程应通过。
2. 杂货铺：等级、收益、公式和界面显示不得充当玩法流程。
3. 角色创建：页面/输入框/预览展示不得充当角色创建流程，确认操作与角色状态落库才是流程。
4. 全新任务：从零生成时同样执行门禁，不能依赖项目名或历史缓存。

每个夹具同时验证后端模型、质量报告、P4 渲染和 P4–P7 门禁。

此外增加项目身份互换测试：保持素材结构不变但替换任务身份，任何缓存、最后有效版本、失败信息和生成正文都不得串入另一任务。

## 非目标

- 不修改用户已经批准的玩法规则。
- 不自动补写证据不存在的机制。
- 不开启 Planning Sketch Phase 3。
- 本轮验证完成前不推送 GitHub、SVN 或正式部署。
