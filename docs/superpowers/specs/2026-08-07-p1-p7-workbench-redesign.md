# P1–P7 策划审核工作台改版规格

## 目标与边界

本轮只重构 P1–P7 页面版式、页面间流转和公开交互状态，不提前执行两份飞书样例的内容颗粒度专项研究。现有任务、已确认目录、交互结论、玩法结论、图解和表格不得因改版丢失或被重新生成覆盖。

目标用户为游戏策划。所有可见文字使用简体中文策划表述，隐藏内部编号、状态码、英文枚举、程序类型和诊断错误。视觉路线采用“克制的精致极简 + 高密度生产力工作台”：白色内容面、浅灰工作区、蓝色主操作、绿色完成状态、黄色仅表示真正需要策划决定的内容。

## 统一流程

上传与任务恢复是七个审核环节之前的共享入口，不占用 P1–P7 编号。七个独立审核环节依次为：

1. P1 确认玩法目录
2. P2 审核交互
3. P3 预览交互交付物与策划草图
4. P4 审核玩法规则
5. P5 审核必要图解
6. P6 审核玩法表格
7. P7 预览并发布完整文档

所有正式工作台显示同一套顶部流程、当前环节、完成状态与返回路径。刷新和任务链接必须恢复原任务及所在环节。按钮必须具有加载、成功、失败和禁用反馈；确认后自动前往下一项或下一环节。P4、P5、P6 是三个独立工作台，不是同页标签，也不能互相挤占布局。

## 共享入口：新建或恢复任务

- 删除无价值的欢迎说明和黑色空预览区。
- 上传截图、基本信息、模型设置和分析进度按自然阅读顺序排列。
- 上传有序截图是主任务；视频为可选补充。
- 未创建任务时不显示正式审核导航；已有任务通过链接直接恢复工作台。
- 分析过程显示真实进度和策划可理解的日志，失败时保留素材、任务和重试入口。

## P1：玩法目录确认

- 左侧展示 AI 对当前玩法的简短理解与证据标签，中间展示动态目录树，右侧编辑所选节点。
- 目录结构支持“玩法系统 → 子系统 → 具体机制”两级或三级动态组织，不套用固定战斗模板。
- 支持改名、排序、合并、拆分、新增和删除；确认时强制保存仍在编辑的输入。
- 主玩法与辅助玩法只能作为当前素材判断，不写死为固定选项。
- 后续所有工作台和最终文档只读取策划确认后的目录。

## P2：交互审核

- 交互审核一次只核对一个真实玩家操作或自动状态变化，主动操作按“操作前 → 玩家操作 → 系统反馈 → 操作结果”阅读；自动触发和信息页使用适配字段。
- 需要策划确认时提供明确选项，不显示孤立的“待确认”。确认当前项后自动进入下一项。
- 确认当前项后自动进入下一项；完成全部交互审核后进入 P3。

## P3：交互交付物与策划草图

- 策划草图以 GVE16 白板逻辑为准：先展示全局页面关系，再展开阶段、复杂页面局部截图和页面内小流程。
- 页面节点必须使用原始截图并保持原始比例；同一页面只定义一次，通过关系线复用。
- 实线表示前进或打开，虚线表示返回或关闭；黄色注记只表示异常、跨状态约束和真正待决策内容。
- 左侧目录只负责定位，中间画板负责表达页面关系；第三份线框的单页详情只能作为节点详情样式，不能把交付物变成孤立页面画廊。
- 红色 1、2、3、4 UE 流转编号本轮不启用，仅保留扩展能力。

## P4：独立玩法规则工作台

- 使用“动态玩法目录 / 本节原始证据 / 策划规则正文”三栏结构。
- 规则正文按机制实际需要展示一句话玩法、正常玩法、关键规则、参数与公式、特殊情况、检查示例和待决策内容；空模块不展示。
- 参数具备策划含义、类型与单位、默认值、上下限、来源、计算顺序、取整方式和算例；无依据值不得编造。
- 有计算关系的章节自动展示参与字段与可建立公式，不限于伤害章节。
- 来源统一表述为素材明确展示、参考文档明确说明、结合上下文判断、策划人工补充或需要策划决定。
- 只有当前规则确认完成，才允许“确认并查看下一节”。

## P5：独立必要图解工作台

- 使用“图解列表 / 图解画布 / 单图审核”三栏结构，每张图可通过、重修或删除。
- 系统自动判断并生成图解，不显示“按需生成”；章节无需图解时明确显示“本章无需图解”。
- 只有多分支流程、真实状态切换、系统输入输出、空间范围、概率池、成长路径或多层效果关系可以生成图解。
- 纯文字步骤、单条公式、普通参数列表、标题加说明式伪图解不得生成。
- 默认隐藏内部图号、节点数、分支数和置信度；证据来源改为策划可读表述。

## P6：独立玩法表格工作台

- 使用“表格目录 / 动态表格 / 行或字段详情”三栏结构。
- 支持属性分类、武器效果、敌人与首领、强化与概率池、关卡波次、配置字段等不同表结构，表头由当前内容动态生成。
- 不把页面降级成程序参数编辑器；类型使用整数、秒、百分比、文本等策划语言。
- 技术表名和字段名只有参考文档明确提供时才保留，并与策划含义分列显示。
- 无依据的 AI 建议值保持为空并提示需要策划填写，不参考“同类游戏”擅自造数值。
- 简单公式使用文本表达；只有复杂关系才交给 P5 图解。
- 没有表格时显示“本项目暂无需要单独审核的玩法表格”，允许直接完成本环节。

## P7：完整文档预览与飞书发布

- 左侧为真实的一级至四级目录，中间预览完整飞书正文，右侧显示检查状态、缺失项、进度与实时日志。
- 同一份文档依次包含策划草图、竞品参考、玩法概述、实际玩法正文、必要图解、玩法表格、配置参数和待确认事项。
- “检查并自动补全”只补缺失内容，绝不覆盖人工确认内容；自动补全后执行主策复检。
- 只要存在可自动修复问题，系统继续修复并显示真实进度；只有确实需要策划决定的问题才停止。
- “已完成、已就绪、完整度”必须与各环节真实状态一致，禁止部分审核却显示可发布。
- 主策检查通过后才启用“导出到飞书”；导出失败保留预览、日志和可重试入口。
- 最终操作只保留返回修改和导出到飞书，避免“导出、发布、确认发布”语义重复。

## 数据与兼容

- 复用现有任务模型和接口，新增视图状态时保持旧任务迁移兼容。
- 已确认内容优先级高于旧版兼容字段；旧逐帧分析默认折叠，不参与正式审核与发布门禁。
- P2 的目录是 P4–P7 的唯一章节结构来源；P3 的页面关系模型同时驱动网页策划草图和飞书原生白板。
- P4 规则、P5 图解和 P6 表格分别保存审核状态，P7 聚合这些真实状态。

## 公开验收入口

测试只通过用户可见边界验收：

1. 页面 DOM 与公开按钮行为：七个环节可进入、可恢复、可确认、可前进和可返回。
2. 现有审核与发布接口：保存目录、交互、规则、图解、表格和最终预览，不直接测试私有函数。
3. 当前任务 `4180cd72eeaa4819be41db50bb4c5011`：数据不丢失，刷新后仍恢复工作台。
4. 浏览器回归：桌面常用宽度下不重叠、不溢出、不出现正文省略号；键盘焦点和禁用状态可见。
5. 文案门禁：策划可见区域不得出现内部英文枚举、`undefined`、内部编号或诊断堆栈。
6. 发布门禁：未完成时自动补全或明确提示，完成后才能导出到飞书。

## 实施顺序

先建立统一外框与 P1/P2，再完成 P3；随后分别实现 P4、P5、P6，最后实现 P7 聚合状态。每个环节采用一条失败测试、一项最小实现的纵向测试驱动循环。完成后运行全部 Python、前端测试和真实浏览器自检，再以主策视角检查信息层级、图文对应、策划语言和任务恢复。

## 本轮明确不做

- 不实现红色 UE 流转编号。
- 不提前执行两份飞书样例的逐字逐图颗粒度专项研究。
- 不合并或重写已确认的当前任务内容。
- 不提交或推送 Git，除非用户再次明确授权。
