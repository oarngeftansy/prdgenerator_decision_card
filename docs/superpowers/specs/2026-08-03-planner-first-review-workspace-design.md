# 面向策划的交互与玩法审核工作台设计

状态：已完成方向确认，等待书面规格复核。

## 1. 目标

把现有偏模型调试、偏数据结构展示的审核工作台，改造成主策和执行策划可以直接使用的生产工具。策划不需要理解“代表帧、component、unknown、跨状态约束”等内部概念，只需要按玩家行为顺序确认事实、补充规则、处理待确认项，并最终输出一份完整的飞书执行文档。

内部仍保留结构化证据、来源 ID、组件关系和置信信息，用于追溯、自动生成及回归检查；这些信息默认不进入策划工作台和最终文档。

## 2. 已确认的产品合同

1. 输入以 2–30 张有序截图为主；视频仅用于补足截图无法闭合的上下文。
2. 内部审核顺序固定为“交互审核 → 玩法审核”。
3. 交互审核只交付两个画板，顺序固定为“策划草图 → 竞品参考”。
4. 不生成独立 UX 设计画板；旧文档中的三画板设计属于历史方案。
5. 交互与玩法最终输出到同一份飞书执行文档，不拆分发布。
6. 最终文档先放确认后的交互画板，再放玩法章节，最后集中列出待确认事项。
7. 工作台不得向策划直接展示内部英文术语、SCN/EVT 等内部编号、证据墙或技术错误原文。

本规格与旧规格冲突时，以本规格及 `2026-07-28-two-board-interaction-design.md`、`2026-07-29-gameplay-review-workflow-design.md` 中仍与本规格一致的内容为准。

## 3. 方案选择

### 方案 A：单步阅读（采用）

一次只审核一个玩家操作，阅读顺序固定为：

> 操作前 → 玩家操作 → 系统反馈 → 操作结果

复杂规则放到对应步骤下；明显缺口就地询问，其余非阻断问题集中到本环节末尾。优点是符合策划复盘交互的自然顺序、认知负担最低，也最容易发现因果链断裂。

### 方案 B：页面总览

同屏展示一个页面的全部状态和控件关系。适合熟悉系统的专家快速扫读，但容易重新变成信息墙，不适合作为默认工作方式。

### 方案 C：泳道流程

按页面、玩家、系统分泳道显示全过程。适合最终流程图，不适合逐条审核；复杂项目中容易出现大量跨线和抽象术语。

结论：工作台采用方案 A；页面总览只作为按需摘要；泳道仅在确实需要表达多角色并行关系时用于最终图示，不作为审核主界面。

## 4. 信息架构与阅读顺序

### 4.1 顶部任务栏

顶部只保留：项目名称、当前阶段、保存状态、阶段进度和主要动作。阶段名称使用策划语言：

1. 确认交互流程
2. 逐步检查页面反馈
3. 预览交互交付物
4. 审核玩法规则
5. 预览并发布完整文档

不再使用“1 流程、2 页面、3 交互预览、4 玩法、5 图解、6 最终预览”这类缺少任务含义的标签。

### 4.2 左侧导航

左侧列出语义化环节名称，例如“选择武器强化”“查看强化结果”“对首领造成范围伤害”，不显示“场景 1、场景 2”。每项显示三种易懂状态：待检查、存在待确认、已完成。

确认当前环节后自动进入下一环节；确认最后一个交互环节后自动进入交互交付预览。若保存失败，保持当前环节并给出明确重试入口，不能表现为点击无反应。

### 4.3 中央审核区

默认一次只展示一个玩家操作，按以下顺序纵向阅读：

1. 操作前：玩家看到什么、处于什么状态。
2. 玩家操作：点击、拖动、选择、等待或自动触发。
3. 系统反馈：即时视觉、声音、动效、数值或状态反馈。
4. 操作结果：页面、玩法状态和可继续执行的动作发生什么变化。

每个区块只显示策划需要确认的描述。截图作为辅助证据按需展开，不以“代表帧”表单形式常驻；组件列表不作为独立审核对象铺在页面上。

复杂规则直接挂在发生作用的步骤下，例如互斥选择放在“玩家操作”，跨页面保留结果放在“操作结果”。不再提供名为“跨状态约束”的抽象编辑区。

### 4.4 右侧辅助区

右侧只保留当前步骤相关的三个模块：

- 本步要确认什么
- 需要补充的问题
- 查看原始截图

默认不展示环节摘要、关键组件清单、模型字段、英文标签和置信度。原始证据在策划主动点击后才展开。

### 4.5 环节结尾

明显且会改变逻辑的问题在对应步骤内就地处理。剩余非阻断问题集中显示为“稍后补充”，允许策划带着这些事项确认环节；这些事项在最终文档末尾统一列出。

结构性错误仍然阻断确认，例如：四步因果链缺失到无法说明本次操作、环节顺序形成断链、所选截图文件不存在。模型置信度低、命名不够精确或非核心细节未知不阻断推进。

## 5. 交互交付预览

交互审核完成后只展示：

1. 策划草图：由确认后的交互结构生成，包含必要截图、红色编号、相邻中文规则、黄色待确认注记和原生直线连接器。前进/打开使用实线，关闭/返回使用虚线。
2. 竞品参考：只包含用户上传的竞品素材，保持用户顺序，不混入策划截图；未提供时显示“待补充”但不阻断。

工作台可提供画板级预览和问题定位，但不向策划暴露内部节点 ID 或编译数据。

## 6. 玩法审核与统一文档

交互交付确认后进入玩法审核。玩法章节从已识别机制生成，不使用固定大问卷；章节可合并、拆分、改名和排序。参数、公式、边界、失败条件和依赖保持结构化，普通审核界面使用中文策划术语。

最终只创建一份飞书文档，顺序固定为：

1. 文档说明与范围
2. 策划草图
3. 竞品参考
4. 玩法章节
5. 必要的玩法图示
6. 待确认事项

不得在玩法部分重复铺设交互截图，也不得把交互和玩法分别发布成两份文档。

## 7. 状态与数据流

1. 视觉分析生成内部证据与候选操作链。
2. 审核模型把截图事件归并为语义化环节，并生成四步阅读数据。
3. 前端只投影策划可读字段；编辑操作继续写回现有结构化审核模型。
4. 每次确认先保存，再切换到下一环节；只有保存成功才更新已完成状态。
5. 完成交互审核后冻结交互修订号并生成两画板预览。
6. 玩法审核引用已确认交互修订；若交互被退回修改，受影响玩法章节标记为需复核。
7. 发布器读取同一任务中的交互与玩法结果，生成一份完整飞书文档。

内部证据数据继续保留，以确保画板生成、问题追溯和既有任务兼容；界面隐藏不等于删除数据。

## 8. 错误处理与点击规则

- 所有主要按钮点击后必须立即进入“处理中”状态，防止重复提交。
- 成功后给出可见状态变化，并按规则自动推进。
- 失败后保留当前编辑内容，显示策划能理解的原因和“重试”按钮。
- 禁止只在控制台记录错误或把后端英文异常直接显示给用户。
- 互斥项使用单选语义；可多选项必须明确写出“可多选”。
- “全部纳入”和“全部排除”等相反操作必须互斥，并在执行前说明影响范围。
- 禁用按钮必须显示原因；可点击元素必须具备悬停、按下和键盘焦点反馈。
- 页面切换、环节切换、截图展开和弹层关闭都要保留明确返回路径。

## 9. 兼容与迁移

- 旧任务中的 `Scene N`、`场景 N` 在加载时优先使用已识别目标和玩家操作生成名称；无法生成时显示“待命名环节”，不回退到数字场景名。
- 旧任务保留的 UX 画板数据不删除，但不进入当前审核、预览和发布流程。
- 代表帧、组件与证据 ID 继续作为内部数据使用，避免破坏两画板编译和历史任务。
- 旧版字段缺失时，从现有操作前、操作、反馈和结果字段生成兼容显示；无法还原的内容进入待确认项。

## 10. 验收与自检

### 自动化验收

- 确认任一环节后进入下一未确认环节。
- 确认最后一个交互环节后进入交互交付预览。
- 保存失败时不推进，输入内容不丢失，并出现可操作的重试入口。
- 四步内容顺序固定，中文标签完整，默认页面没有 `unknown`、`component`、`entry`、`result` 等内部英文。
- 互斥控件不能同时处于选中状态；多选控件行为符合说明。
- 两画板标题、顺序和素材边界正确。
- 最终发布只生成一份文档，交互内容位于玩法章节之前。

### 浏览器回归

至少覆盖：全流程鼠标点击、键盘操作、环节自动推进、返回修改、刷新后恢复、保存失败重试、空竞品素材、超长中文内容、窄屏与常用桌面宽度。

### 主策视角自检

实现后以“第一次接触该项目的主策”为标准逐页检查：是否知道当前目标、下一步动作、当前结论、阻断原因和最终产物；是否存在技术术语、重复信息、错误阅读顺序、点击无反馈或状态冲突。问题按 P0–P3 输出：

- P0：数据损坏、无法继续或发布错误。
- P1：主流程阻断、确认错误、交付内容错误。
- P2：明显理解成本、交互不一致或重要反馈缺失。
- P3：视觉细节、次要文案和非关键效率优化。

## 11. 本轮实现边界

本轮完成工作台信息架构、中文化、四步审核、自动推进、交互状态反馈、两画板入口和统一发布路径的前端与必要后端适配。保留现有结构化模型和飞书生成能力，不在本轮重写视觉分析算法，也不新增与已确认交付无关的协作、权限或版本管理功能。
