# Executing Staged Acceptance

## Overview

把“实现完成”和“阶段完成”分开。阶段只有在验收用例经用户确认、真实环境自检通过、证据可复核、测试数据已恢复且用户明确验收后才能完成。

## Hard Gate

严格按以下顺序执行，不得合并或跳过：

1. 完成本阶段实现，但保持状态为 `in_progress`。
2. 向用户提交验收用例，逐条写明前置条件、操作、预期结果和拟截图证据。
3. 等待用户明确确认用例。确认前不得开始正式自检。
4. 严格按已确认用例在真实浏览器或真实目标环境中自检。
5. 每个关键状态保存截图，并记录用例编号、页面、前置条件和观察结果。
6. 发现失败时立即保持或退回 `in_progress`，先补失败测试，再修复并重跑相关用例。
7. 恢复注入的测试数据，核对正式任务无污染。
8. 运行相关自动化回归和数据完整性检查。
9. 向用户展示逐条结果、截图、自动化证据、限制和不适用分支。
10. 等待用户人工验收。只有用户明确说通过后，才标记阶段完成并进入下一阶段。

## Acceptance Case Contract

每条用例必须包含：`ID`、目标、前置条件、操作步骤、预期结果、截图清单、清理要求。条件分支若无法在当前正式数据中触发，标记为“本轮不适用”，并说明原因与替代自动化证据；不得声称已有截图证明。

若阶段涉及决策卡，必须读取 [references/decision-card-stage-1.md](references/decision-card-stage-1.md) 并继承 TC1–TC9。

## Evidence Contract

- 截图存入 `artifacts/<stage>-browser-acceptance/`，使用稳定、可辨识的文件名。
- 截图必须同时显示页面身份与目标状态；空白、滚动错位或无法定位页面的图片无效。
- 最终汇报用绝对路径内嵌截图，并把每张图绑定到具体用例。
- DOM 断言和自动化测试只能补充截图，不能冒充真实浏览器证据。
- 非视觉分支可以自动化验证，但必须明确标为自动化证据。
- 自检后记录数据恢复结果，例如决策卡数量、claims、确认状态和版本是否回到预期。

### 策划草图到玩法正文的跨载体门禁

- 对策划草图中的页面状态、玩家操作、系统反馈、结果状态和可见属性逐条判断是否具有玩法意义。
- 具有玩法意义的解读必须记录来源环节、来源截图、目标玩法章节和承载位置，并同步到 `normalFlow`、`keyRules`、`specialCases`、参数命名或配置表之一。
- 纯页面布局、控件坐标和空间连线保留在策划草图，不得为追求覆盖率重复写入玩法正文。
- 同步结果必须输出 `delivered`、`board_only` 或带改善路径的失败状态；存在目标章节缺失或正文落点缺失时，不得开放 P7/飞书导出。
- 正式证据必须展示逐条映射表及遗漏数量；只展示草图截图或正文截图不能证明跨载体同步完成。
- “武器与强化属性”等画板分组中的具名武器、具名强化和明确效果属于对象业务事实，必须进入对应对象的 `attributeSections`。诸如“画面包含等级信息”、控件位置和布局描述仍为 board-only。截图值采用“本次截图显示”的正文表述限定证据范围，不附加审核过程说明。

固定执行以下跨载体验收用例：

1. 画板中的具名业务事实必须出现在对应载具、武器、怪物或关卡正文小节，并保留来源截图映射。
2. “画面包含等级信息”、槽位存在、按钮位置、控件坐标和布局描述不得进入玩法正文。
3. 同步报告 `missingCount` 必须为 0，P7 与待发布飞书载荷必须逐条包含相同正文。
4. 扫描全部核心对象；没有具名证据的对象不得为了覆盖率自动补写。

正式截图至少包含画板事实、对应正文、遗漏数为 0 的报告以及 P7/飞书载荷一致性结果。

### 图解与正文连续性门禁

- 流程图不得截断一个编号列表、同一状态机说明或同一属性分组。完整业务规则先连续呈现，图解随后紧邻该规则组。
- `afterFlowIndex`、`followUp`、审核提示和编辑说明只属于内部元数据，不得直接进入正式正文。
- 禁止“图中的内容由后续章节展开”“本节继续说明”“流程图只确定”等 AI 导航或审核口吻。只有新增业务事实才可成为图后文字。
- 验收截图必须同时覆盖图前完整规则组、图解和图后首段，证明编号连续且不存在导航旁白。

### 嵌入式工作台响应式门禁

- P7 等嵌入式页面不能只按浏览器 viewport 切换布局；必须按实际工作台容器宽度验证。
- 三栏空间不足时，状态与飞书导出区必须整块换行或变成单栏，中文不得逐字换行，按钮不得越界，也不得通过隐藏关键操作规避问题。
- 验收至少覆盖正常宽度、窄容器和极窄容器，并截图证明正文、状态说明和导出按钮均完整可读。
- 同时检查组件内部级联：飞书授权说明与导出按钮在侧栏中必须纵向排列，通用横向 flex 不得覆盖 P7 专用布局。

### P7 与飞书原生表格门禁

- 同源预览中的飞书原生 `<table>` 必须保留真实 `thead/tbody/tr/th/td` 结构，不得文本化或把表头拼成段落。
- 本地预览允许增加样式类和横向滚动容器，但不得改变飞书发布 XML 的单元格、行列顺序和值。
- 逐表核对表头列数、每行单元格数、边框、内边距和窄宽度横向滚动；任一行列数不一致或表头粘连均不得验收。

### 正文小标题密度门禁

- 同一连续列表达到 8 条以上且跨越多个明确业务主题时，应合并为 2～4 个内容特定的小标题，每组继续使用分点。
- 小标题必须由该章节的对象、阶段和动作产生，不得把首领章节的标题复用到奖励、武器或载具章节。
- 相近重复句先合并；禁止整页无分组罗列、每条单独起标题以及“其他规则”“规则与边界”等兜底模板标题。
- 验收同时检查目标长列表和至少一个无关章节，证明分组生效且标题没有跨机制污染。

### 图解审核故障门禁

- 图解用例必须同时检查语义、状态和动作目标。语义检查覆盖玩家操作、系统处理、判断、分支、循环、汇合与结果；不得用“出现箭头”或 SVG 已渲染替代主策判断。
- 左侧章节、中间图解、右侧审核对象必须绑定同一图解 ID。切换后提交一次审核，并从网络请求或后端模型核对实际写入的 ID，不能只看界面高亮。
- 统计、绿色圆点、已通过文字、完成度与下一步门禁必须逐项对照后端真实状态；过期图解显示“需更新”，普通未决显示“待审核”，只有 reviewed 才显示绿色“已通过”。
- 更新过期图解时必须原位更新，保留 ID 与章节绑定、版本递增、状态回到待审核；不得重复生成单章图，也不得让通用生成器覆盖策划语义图。
- 用户判退任一图或证据时，立即停止继续审核与批量点绿，退回 `in_progress`，撤销误写结论，记录失败截图和改善路径，修复后重新提交该组图供人工判断。
- 用户已经逐项明确通过但界面故障写错目标时，可在修复并用失败测试证明绑定问题后，按用户已表达的结论补写遗漏状态；补写后仍须展示6/6等真实汇总、下一页跳转和刷新恢复证据。

### 参数审核状态一致性门禁

- 先区分逐行参数审核表与业务配置整表。只有 `chapter_parameters` 或明确包含“状态/操作”审核列的表可以显示 `已确认行数/总行数`；载具、武器、怪物、波次等动态业务表只显示“整表待审核/整表已通过”，不得拿业务列值计算审核进度。
- 顶部汇总、每张表状态、目录标记、完成度和进入 P7 的门禁必须读取同一组活动表及有效 reviewed 状态。任一活动表未通过，均不得因“最后一张已通过”而开放 P7。
- 多表章节必须逐表验证动作目标：点击目标表的“通过本节”，从网络请求核对 table ID，从后端模型核对该 ID 的状态，再刷新页面确认状态仍在。只看按钮、提示或局部重绘不算保存成功。
- 状态文案不得互相矛盾：同一张表不能同时显示“已通过”和“0/N 已确认”；过期表必须显示待重新审核含义，只有真实 reviewed 且逐行门禁（如适用）完成后才能计入已通过总数。
- 诊断若需要在正式任务实点审核，只能选择用户已经表达通过意图的对象，并明确记录被写入的表；不得为了凑齐完成度替用户批量通过剩余表。
- 审核、重修或逐行确认触发规范模型重建时，必须保持当前 table ID；不得自动回到第一张表。验收同时覆盖动作返回后的选中对象和整页刷新后的选中对象，并核对请求 table ID 与屏幕对象一致。

### 跨页路由竞态门禁

- P1–P7 路由验收必须在同一浏览器会话连续执行，并在每页等待规范模型同步与可能的预览请求完成；逐页独立冷启动只能作为补充证据。
- 每页同时核对 job 参数、`ui` 参数、顶部当前步骤、实际可见根节点和规范模型允许路由。画面正确但 URL 错、URL 正确但顶部步骤错，均判失败。
- 任何旧异步请求完成后都不得覆盖较新的显式 URL 或用户点击导航；需要用导航意图版本使旧回调失效，并在最终同步后重新校正 URL。
- 从带 `ui` 的深链冷启动后，必须在规范模型仍在加载时立即点击另一个阶段，并继续观察到全部请求结束；初始化时缓存的 URL 阶段只有在导航意图版本未变化时才允许重新应用。
- P7 的“返回修改”和“处理未完成项”是两种不同动作：前者可回到固定编辑页，后者必须按规范模型定位第一个真实阻塞阶段；不得共用同一固定跳转回调。
- 规范模型重建、玩法模型重建和预览回调都必须保留等待期间用户最新选择的页面；只有明确的确认/继续动作可以主动推进阶段。
- 历史任务载荷已经包含玩法模型时，应先同步建立可渲染的玩法工作区，再开放 P4–P7；不得出现“按钮已启用但目标根节点尚未创建”的空白跳转。
- 页面内部的“继续、进入下一步、确认后前进”和顶部阶段导航必须复用同一原子跳转契约：更新导航意图版本、选择实际可达页面、重绘、同步实际 `ui`、持久化。只切换 DOM 面板或只更新 URL 均判失败。
- 异步确认、图解审核和参数审核开始时记录导航意图版本；响应返回后只有版本未变化才允许自动前进。验收固定加入“请求未完成时点击另一阶段，旧响应返回后仍停留在用户最新页面”。
- 中间环节和最后环节都必须有可执行的推进按钮；最后环节不得因为缺少下一条 transition 而禁用，必须在确认后原子进入下一阶段。
- 从交互审核进入玩法审核等跨业务域跳转，必须先持久化后端交接状态并重新读取规范模型，再切换页面；只切本地 DOM 或 URL 不算通过。

### 可编辑目录的操作真实性与清理门禁

- “取消”必须丢弃当前未提交草稿；不得由输入框失焦或 `change` 在取消动作之前偷偷写入正式任务。只有明确保存动作可以提交编辑器内容。
- 添加、删除、上下移动、合并、拆分和所属模块切换均须命中规范模型，而非只修改 DOM。所属模块单选必须刷新可恢复，并可通过玩法历史撤销。
- 共享撤销/重做按钮必须按当前页面选择正确的数据域：目录、玩法规则、图解和参数操作使用玩法历史；交互流程操作使用交互历史。
- 每次写请求必须记录并核对目标 ID、操作类型、整数 `expectedRevision`、响应状态和后端结果。任何缺 revision 或 409 均判失败，不得以最终画面看似正确放行。
- 可逆自检结束后必须恢复章节数、标题、顺序、所属模块、正文和确认状态；仅内容相同但状态退回 draft 仍属于数据污染。

### 交互画板推进与隐藏页面门禁

- 适配、居中、缩放、全屏等画板按钮必须产生可观测的视口变化；空回调、仅改按钮文字或目标已经在初始位置而无法证明动作，均不得判通过。
- “应用并查看下一环节”必须依次完成保存、确认、保持当前语义页面、选择下一环节。复用通用确认函数时，必须覆盖其旧页面路由副作用并同步 URL。
- 验收不仅检查目标节点是否存在，还要检查它是否可见、可操作且属于当前 active view；节点留在隐藏旧页面中视为跳转失败。
- 刷新恢复环节选择时，应核对选中索引、stage/transition ID、编辑器对象和持久化 UI 状态一致；自检快照必须在显式选择目标对象后建立。

### 全链路浏览器证据与隔离门禁

- P1–P7 必须统一覆盖 1920、1280、1024、768、390 五档宽度。逐页检查主操作可见、中文不逐字换行、三栏在窄宽度改为可读的单栏或双栏、业务表格保留横向滚动；用 `overflow:hidden` 截掉内容不算响应式通过。
- 同页渲染多个流程图或画板时，SVG 的 marker、gradient、clipPath 等 `id` 必须按图实例作用域生成，并验证页面不存在重复 ID；只检查单张 SVG 外观无法证明引用没有串图。
- 对话框、证据抽屉和浮层必须在节点插入 DOM 后再聚焦。固定验证打开后焦点进入浮层、Escape 关闭、焦点回到触发器；重绘时不得被通用焦点恢复逻辑抢回旧节点。
- 折叠目录必须从真实 DOM 的 `aria-expanded` 读取状态，并验证收起、展开两个方向及子项可见性。测试 mock 的属性对象不能替代浏览器字符串属性。
- 每个会写数据的浏览器用例使用独立任务副本或在运行前恢复同一基线哈希；不得串行复用前一用例已修改的审核数、选中项或完成度，再把固定总数失败误判成产品回归。
- 计数断言优先验证相对变化和幂等语义：未通过对象采用一次只增加 1，已通过对象重复采用不增加；两者都必须恰好发送一次请求，并保持当前章节、对象和刷新恢复状态。
- 验收截图按 SHA-256 去重。相同画面不得以不同文件名冒充多个证据；最终包每个哈希只列一个代表图。浏览器历史、请求次数、持久化 ID 和数据哈希等非视觉事实使用结构化日志佐证，不伪造截图。

## Completion Report

按“阶段结论 → 用例结果 → 截图证据 → 自动化回归 → 数据恢复 → 限制/不适用项 → 请用户人工验收”的顺序汇报。任何一项失败、缺证据或用户未确认，都不得使用“阶段完成”“验收通过”或进入下一阶段。

## Red Flags

- 先自检、后请用户确认用例
- 只报测试通过，没有真实页面截图
- 截图与用例、页面或前置条件无法对应
- 用测试造数后未恢复正式任务
- 把未触发分支写成已截图验证
- 用户尚未明确通过就更新阶段状态

出现任一项：停止完成声明，退回对应步骤。
- 验收入口必须区分裸首页与案例深链：裸 `/` 用于新用户从零开始，`?job=<id>&ui=<view>` 仅用于查看或继续指定案例；最近任务缓存不得让裸首页自动进入旧任务。
- 阶段页面存在数据后必须始终可进入查看。完成门禁只限制“确认通过、继续、导出”等结果动作，不得复用为阶段导航禁用条件；验收时逐项点击全部阶段并核对 URL 与可见面板同步变化。
### 上传、失败与重试的数据门禁

- 创建任务前确认当前页面没有正在运行的任务，连续点击只能产生一个任务 ID。
- 质量失败时核对三套证据：原素材数量、已落盘合格分析数量、仍需重试数量。界面百分比必须对应合格率，不得展示旧的管线进度。
- 点击“重试任务”前记录失败任务 ID；请求 URL、后台写入目标和返回任务 ID必须仍是该任务，不能落到历史完成任务。
- 重试只能请求未达标素材；已合格分析的内容和哈希在重试前后保持一致。
- 新任务、失败任务和正式案例任务必须隔离。任何测试前后都要比对正式任务摘要，禁止用正式任务验证有写入的操作。
- 新素材覆盖测试必须从一个带 `?job=<旧任务>` 的案例页开始：展开 API 设置、选择新截图、点击开始分析；确认 URL 已解除旧任务、项目名和素材保持为新任务，旧任务迟到响应不能把页面切回历史案例。
- 验收“开始分析”按钮时必须覆盖无 Key 分支：API 配置区应展开、焦点进入 Key 输入框、素材与当前项目保持不变、URL 不恢复旧 job，且不得出现未定义函数或“后端连接失败”的误报。
- 所有跨 P1–P7 的按钮验收都要同时检查三项：目标页面已显示、URL 的 `ui` 已更新、刷新后仍停留在同一页面。仅检查点击后的视觉切换不得判定通过。
- 浏览器证据中应记录实际加载的 JS 缓存版本；若版本落后于仓库，先重启最新服务并强制加载新版本，再判断功能是否失败。
- 上传数量上限必须在页面提示、前端校验、后端请求校验和素材落盘服务中保持一致；验收固定覆盖最小值、常用大批量值、最大值和最大值加一，按钮禁用时必须显示具体原因。
- `failed` 任务始终保留“进入工作台”：有历史审核模型时恢复原 P1–P7；没有审核模型时进入只读失败工作台，展示实际错误、保留素材和配置模型／重试／返回素材动作。失败状态只能限制确认和导出，不能限制查看与恢复。
- 失败工作台打开时立即固定失败任务的 `job` 与 `ui=analysis_failed`；若重试前需要配置模型，保存并恢复完整失败页 URL。真实点击重试后必须证明只有一个 `/api/jobs/<失败ID>/retry` 请求，不能只证明按钮可见。
- 同一用例可有多张连续状态图，但不同用例不得默认引用同一截图。若最终画面客观相同，必须补拍该用例独有的可见前置、焦点或选择状态，并用请求记录或状态 JSON 佐证，不得靠改名复制图片。

### 历史玩法目录迁移门禁

- 旧任务的 claim 缺稳定 ID 时，模型加载必须补 ID；目录 entry 缺 `claimIds` 时，按 canonical chapter claims 回填归属，并保留真正未归属 claim。
- 合并/拆分验收不能止于按钮存在。必须真实打开选择面板，看到可选章节或 claim，执行可逆操作，并在验收后恢复章节数量、归属、确认状态和 revision。
### 图解数量与关联章节一致性门禁

- P5 左栏若按章节切换，标题必须写“关联章节”，计数使用实际可见章节入口；不得写成“图解列表”后显示另一种实体的数量。
- 图解摘要按去重后的活动图解统计。已通过、待审核、需更新、需重新确认必须互斥，状态合计必须等于图解总数。
- 固定加入共享图解用例：一张图同时关联两个或更多章节，验证章节导航数量可以大于图解数量，但界面不会让用户误认为漏图、重复图或统计失效。
- P5 切换关联章节后必须持久化真实章节 ID；重绘和刷新后同时核对 `aria-current`、章节文本和右侧图解归属。恒定空 ID 或默认首项不得作为恢复证据。
### 飞书授权与保存目录门禁

- 首页发布区、P7、重新导出、另存新版本等所有入口必须调用同一授权感知发布链；任何入口直接调用裸发布接口均判失败。
- 未授权用户点击导出：打开飞书官方授权页；授权完成后自动返回目录选择，不要求重新点击导出。
- 首次发布/另存新版本：必须提供“我的空间 / 言灵镜瞳”默认项和有权限文件夹浏览；取消不得创建文档。
- 重新导出：更新原文档并保留原目录；部分失败重试复用原 request ID、document token、folder token，禁止重复创建。
- 发布请求必须携带已选 folder token，后端固定并校验该 token；成功状态显示实际保存位置，但公开响应不得暴露文档、画板或授权 token。
- 固定验收：默认目录、选择子文件夹、返回我的空间、取消、确认、授权后续接、重复点击幂等、失败重试、另存新版本、成功位置显示及恶意文件夹名转义。

### 主策工作流去重与页面身份门禁

- 同一业务动作在同一视口内只保留一个主入口。若底部固定操作栏已经包含保存、通过和前后切换，页头不得再复制保存或通过按钮；重复入口会让策划无法判断哪一组才是最终提交。
- P1 的新增系统与新增章节只能各有一个明确入口。空状态可以解释下一步，但不得再渲染第二个同义新增按钮。
- P6 左侧只负责切换章节；同一章节的多张表必须同时可见并逐表审核。不得在每张表内复制“上一节/下一节”，也不得在保存后从“同章多表”突然折叠为单表。
- P6 每表动作使用“重新生成此表/通过此表”，动作必须携带真实 table ID；整页只保留一个“进入文档预览”，并由所有活动表的统一审核状态控制。
- 保存、重绘和刷新后恢复当前 table ID 所属章节，并保持目标表可见；不得自动回到第一张表或改变当前章节。
- P7 顶部是交付准备进度，不是第二套页面导航。无论哪个前置项未完成，当前页面都必须明确标记为“文档导出”；未完成项保持 pending，并在右侧列出真实阻塞原因。
- P1–P7 的名称和顺序必须在全局导航、P7 顶部进度、右侧状态和完成度数据中一致：规则审核 → 图解审核 → 参数审核 → 文档导出。禁止出现“图鉴审核/图解审核”混用或图解、参数顺序颠倒。
- 正式验收固定检查每页可见按钮文本去重、当前页 `aria-current`、真实 `ui`、刷新恢复、选中对象 ID、门禁来源和同一视口内的重复操作数。

### P1–P7 门禁可理解性契约

- 每一步的主操作旁必须就近显示三类信息：当前还缺什么、完成后进入哪个明确页面、为什么此刻不能继续。不得只显示灰色按钮、百分比或“待处理”。
- 禁用主操作必须通过可见说明和 `aria-describedby` 指向同一门禁文案；文案使用策划可理解的业务名和数量，例如“还需通过 2 张表，全部通过后进入文档预览”。
- 门禁应在当前步骤首屏可见，可使用内容流内的 sticky 区域，但不得以浮层遮住正文、审核卡片或底部操作。390–1920 宽度均需验证按钮完整、文案自然换行且无横向溢出。
- 自动前进同样需要说明目的地。P4 最后一章通过后进入图解审核，P5 全部图解通过后进入参数审核，P6 全部表格通过后进入文档预览；异步处理中应显示处理中状态并阻止重复提交。
- P7 必须列出真实阻塞项，并说明“处理未完成项”会跳到第一个阻塞步骤；“返回修改”与“处理未完成项”不可复用一个固定目标。
- 门禁只限制确认、继续、生成和导出，不限制用户进入任一步查看现有内容。验收同时检查按钮可视、遮挡、禁用原因、URL、目标根节点、刷新恢复和浏览器前进/返回。
## Return and asynchronous-save matrix

For a multi-step workbench, acceptance must cover browser Back/Forward and every visible return action: previous, return to edit, return to assets, failed-task return, and authorization cancel. Assert destination view, job identity, current selection/scroll target, and persistence after refresh.

When inspecting already-generated later artifacts, a successful item save may remain on the current phase or advance, but must never auto-route backward to the earliest incomplete gate. Backward routing requires an explicit user action.

For diagram/table/parameter saves, prove that exactly one request was made, the counter/status updated immediately, the selected chapter/artifact did not reset, and refresh restored the same target. When interaction and gameplay models hydrate separately, the dedicated gameplay response is authoritative; reject stale embedded snapshots.
